## 4. 逐条根因（带证据）

### 4.1 Go / 4.2 Pascal / Kotlin —— 条件跳转**确实**打到了寄存器，但拼法是 `L0` 不是 `R24`（v0.96.192 定案）

> ⚠ **本节替换掉了 v0.96.191 那一版"复核"——那一版是错的，撤回。**
> 当时我 grep 的是 `j[..] R<数字>`，**没认出 `L0`–`L7` 本身就是长整数寄存器（R24–R31）的拼法**，
> 于是得出了"全树没有任何前端把跳转目标写成寄存器"的错误结论。
> 报告初版的**方向是对的**，只是它写的 `jge R24` 应该是 `jge L0`。

**机理**（`VMLAssembler.ParseOperand`）：

```csharp
// 长整数寄存器：L0-L7 (映射到 R24-R31，与运行时一致)
if (operandStr.StartsWith("L", ...)) {
    if (int.TryParse(operandStr.Substring(1), out int regNum) && regNum >= 0 && regNum <= 7)
        return new Operand(OperandType.REGISTER, regNum + 24);
}
```

而四个前端**自己拼**标签名时写的是 `$"L{labelCounter}"`（基类 `NewLabel()` 用的是 `L_{n}`，
带下划线、`int.TryParse("_0")` 失败，本就安全）：

| 前端 | 文件 | 现象 |
|---|---|---|
| **Pascal** | `CodeGenerator.Misc.IO.cs` | 数组越界检查的两条分支**都不跳** ⇒ 落进"越界 → 退出" ⇒ **一帧不出**（已修，patch 0013）|
| **Go** | `CodeGenerator.Core.cs` | **死循环**（`--vmtimeout` 杀、一帧不出）⇒ 已修后**出帧**（patch 0014）|
| Forth | `CodeGenerator.cs` | 同形，未单独复现（patch 0014）|
| C | `CodeGenerator.Expressions.Types.cs` | 同形。C 一直是对的**是运气**——它另有 `L80190001` 形态的大数字标签（`regNum <= 7` 不成立 ⇒ 落回标签分支），而这个 `GenerateLabel()` 只在 3 处用（patch 0014）|

**为什么只在"标签编号 < 8"时冒头**：程序短、计数器还没到 8 就已经踩完了 —— 这也解释了
为什么 22 个前端里只有这几门中招、而且症状各不相同。

**它的表现是"静默"的**：`ExecuteJmp` 只处理 `LABEL` 与 `IMMEDIATE`，**寄存器操作数两个分支都不匹配
⇒ 什么都不做**、直接往下执行。没有报错、没有崩溃，程序只是**走进了不该走的那条路**。

### 4.2' Pascal —— 数组已通（v0.96.192）

**定位过程**（这段本身值得记，因为中间我自己做过一个**无效实验**）：

1. 二分到"**写**那一步"就跑飞（写之前开一次窗出帧、写之后不出）。
2. 把两处越界早退换成**可区分的标记**（`syscall #590` / `#591`，`--trace` 会打号）
   ⇒ **两个都触发** ⇒ 两条条件跳转**都没跳**。
3. 把生成物里的标签整体改名（`L0` → `ZZ0`）再跑 ⇒ **立刻出帧**。**这一步定案。**
4. ⚠ **无效实验**：我手写汇编用 `L0` 当标签、量出来"跳了"，于是以为跳转没问题 ——
   实际那个探针里**跳与不跳都落到同一句** `move R0 #10`，量出来都是 10。
   **判据必须让两种结果落在不同的地方**，否则它只是在确认自己。

**验证**（全部逐像素量，画布 200×200）：

| 探针 | 结果 |
|---|---|
| `a[3] := 5; s := a[3]` 画宽 `s*10` | **50** ✓（= 5×10）|
| **游戏心跳**（开窗 → 定时器 → `ui_wait_msg` → 累加 → 重画 → `ui_present`）| **4 帧**，末帧绿条 **60 = 3×20** ✓ |

⇒ **Pascal 四关 + 游戏心跳全过**（实际游戏尚未写）。

附带修掉的一处（独立成立，但不是这次的病根）：数组元素地址方向写成了
`base − (i − 下界) × 4`，而数组块在数据段里是**向上**排的 ⇒ 下标 ≥ 下界+1 会写到数组"前面"。
已改成 `ADD`（patch 0013）。

心跳探针 = `.scratch/pasheart.pas`（由 Go 那个 `.scratch/goheart.go` 改写，跑法一样：
`--sim "t;t;t;t;t"` 脚本化投递计时器消息）。

### 4.2'' Go —— 数组三处补齐 + 栈帧少算（v0.96.193）；**四关 + 游戏心跳全过**

patch 0014 修掉标签洞之后，Go 的死循环好了，但数组还是坏的 —— 实测 `a[2]`→8、`a[5]`→20、
`a[7]`→28，**全是 `idx*4`**（= 地址当值）。读汇编看到**三处都缺**，不在一个地方：

| # | 缺什么 | 修法 |
|---|---|---|
| ① | `var a [8]int` **不分配** —— 只按 `GetTypeSize`（默认 4）留一个槽、从不初始化 | 用基类现成的 `AllocateVmlArray`（布局 `[count, e0, …]`）建块，把**块地址**存进变量槽 |
| ② | `a[i] = v` **整段没有代码生成** —— 赋值目标是下标时谁都不认，右值算完就丢（`a[3]=5` 只编出一句 `move R0 #5`）| `GenerateAssignment` 补 `IndexExpr` 分支：值先进 R2，再算 `base + idx*4 + 4`，最后 `MOVE [R0], R2` |
| ③ | 读取结尾是 **`MOVE R0, R0`（空操作）**，且偏移**少跳 VML 数组头** | `MOVE R0, [R0]`；偏移补 `+4`。字符串索引分支同族（`MOVEB [R0], R0` → `MOVEB R0, [R0]`）|

③ 与 Swift 的 patch 0011 ③ 是同一个病（**操作数写反**）—— **"地址当值"族第六次**。

**另外一处更隐蔽的**：`CalculateLocalSpace` **只看块里的顶层语句**，
`for i := 0; …` 里的 `i` 与循环体内声明的变量都没算进去 ⇒ **帧开小了**，
局部变量落到保留区之外，而表达式求值的 `push`/`pop` 正好写在那里
⇒ **每次求值都把循环变量冲掉**。症状极具迷惑性：

```
for i := 0; i < 5; i++ { s = s + a[3] }   → 只累加 2 次（10 而不是 25）
for i := 0; i < 5; i++ { s = s + 1 }      → 又是对的（50）
```

差别只在"循环体里读了一次数组"（多了几条 `push/pop`，恰好踩中）。
**少算 ≠ 只浪费空间，少算就是踩内存** —— 现在递归进 if / for / switch 统计，宁可多算。
同批还修了 `GenerateLocalVarDecl` 里 `Mem($"R14-{-localVarOffset + typeSize}")` **多一个负号**
（`R14--4` 被解析成 `R14 + 4`，往调用方写）⇒ **`var x int = 5` 的初值从来没生效**。

**验证**（画布 200×200，全部逐像素量）：

| 探针 | 结果 |
|---|---|
| `a[3] = 5; a[3]*5` | **25** ✓（改前 60 = 12×5）|
| `a[1]=3; a[4]=7; a[7]=9` 各画一条 | **30 / 70 / 90** ✓ 三个互不串 |
| `for i<5 { s = s + a[3] }` | **25** ✓（改前 10）|
| `for i<5 { s = s + 1 }` | **50** ✓ |
| **游戏心跳**（开窗 → 定时器 → `ui_wait_msg` → 累加 → 重画 → `ui_present`）| **4 帧**，末帧绿条 **60 = 3×20** ✓ |

⇒ **Go 四关（编译出图 / 循环 / 数组 / 函数）全过，游戏心跳也验过了** —— 与 Swift / C# 同一条线。

#### 续 v0.96.195：写成真的贪吃蛇之后，又挖出**两条**（patch 0017 + 0015 增补）

**（一）控制语句头部里的复合字面量 —— 一条 bug 假扮成四条语法限制。**
`for i < A[1] {` 的那个 `{` 被 `ParseExpressionSuffix` 当成 `A[1]` 的**复合字面量**，
整个循环体被当元素列表吃掉。报错却是 `Expected RBRACE, but got IF`（位置指向被吞掉的
循环体第一条语句）⇒ 第一轮误判成"循环体里 `if` 必须排在赋值之前""不能嵌套循环/`if`"
"函数不能带参数"，把整份代码改成了扁平风格。修法：控制语句头部（`if`/`for`/`switch` 的条件、
`for` 的 init/post）里禁止复合字面量 —— Go 规范本来就这么规定。修完实测
**嵌套循环、嵌套 `if`、循环体里 `:=`、先赋值再 `if`、带参带返回值** 一次全过（`.scratch/goprobe.go`）。

**（二）形参只搬了第一个 —— 又是"操作数写反"+ 少算一个槽位。**
函数序言写着"第一个参数在 R0 里"，只搬了 `[R14-4]` 一处。实测**除末参外全是垃圾**：

* 偏移少算了 **CALL 自己压入的返回地址**那 4 字节 ⇒ 应为 `[R14+8+4*i]`（`[R14+4]` 是返回地址）；
* 那一支还**操作数写反**：`MOVE [栈槽], R0` 的 dest 在前 ⇒ 那是"把 R0 存回调用方的实参槽"，
  等于用最后一个压栈的值（= 第 1 个实参）把 4 个实参槽全冲掉。

修完实测三参函数逐个精确：`rep(3,5,7)` → 三条矩形宽 **30 / 50 / 70** ✓，
`add(4,3)` → 70 ✓，`five()` → 50 ✓，嵌套循环 `grid()` → 40 ✓。

**还剩两条真的限制**（都写进了 `Examples/go/snake.go` 的文件头）：

* **字符串拼接编出来是空串**：`"AB" + "CD"` 渲染出来一个字都没有（`GenerateBinaryOp_StringConcat`
  手写的那段汇编有问题）⇒ 分数只能用分数条画。
* **函数名别和标准库撞**：自定义 `func sum(...)` 会被链接到 `lib_util_sum`、**静默调错函数**
  （编得过、结果莫名其妙 —— 实测排查了半小时才定位）。

⇒ **Go 贪吃蛇写成了**（`Examples/go/snake.go`）：蛇头 248px（1 格）/ 蛇身 496（2 格）/ 食物 248（1 格）
逐像素精确，12 拍定时器后每拍右移一格、吃到食物变长、撞墙后弹框重开。

### 4.2C Kotlin —— 数组路径四处明摆着的缺陷已修，**但数组读仍未解决**（v0.96.194）

> ⚠ **v0.96.196 补记（未核实）**：用户在真机上反馈"**Kotlin 也正常**"。
> 下面的结论是**我量出来的**（判据：把读到的值当 x 坐标画、逐像素看），
> 两者不一定矛盾（"Kotlin 能编能跑" ≠ "数组读对"），但**也可能是这一轮判定错了** ——
> 本报告已经出现过一次自我推翻（§4.1 的 `L0`）。**再动 Kotlin 之前先问清"跑的是哪个程序、
> 有没有读数组"**，确认之后再决定是"修"还是"撤回并复核"。

Kotlin 与 Pascal 症状同族，但它的标签走基类 `L_{n}`（安全）⇒ 真因另找。读汇编看到
**四处各自独立、且都在汇编层面自证是错的**缺陷（`patch 0016`）：

| # | 原来的写法 | 为什么一定是错的 | 改成 |
|---|---|---|---|
| ① | `MOVE R0, [R1+off]`（写数组字面量的元素）| **dest 在前** ⇒ 这是**从数组读**，元素值根本没写进去 | `MOVE [R1+off], R0` |
| ② | 下标一律按**字符串那套**（`addr+idx`、1 字节、不跳数组头）| 布局是 `[count, e0, …]`，元素 i 在 `base + i*4 + 4` | 数组走 `idx*4+4`，并用标记区分字符串 |
| ③ | "load byte" 是 `MOVEB R0, R0` | **自赋值、空操作** ⇒ 地址被当成元素值 —— **"地址当值"族第七次** | `MOVE(B) R0, [R0]` |
| ④ | `arrayOf` 只把 count 放进 R0 就 CALL | 被调用方 `array_alloc` **按 C 约定读 `[R12+12]`** ⇒ 分配尺寸与返回指针都是垃圾 | 先 `PUSH R0` |

**仍未解决**：修完四处后读数**只对下标 3**（`arrayOf(10,20,40,80)`，把值当 x 坐标量）：

| | `a[0]` | `a[1]` | `a[2]` | `a[3]` |
|---|---|---|---|---|
| 实测 | 0 | 0 | 0 | **80** ✓ |
| 期望 | 10 | 20 | 40 | 80 |

而且读数**会随元素的值变**（换成 `arrayOf(2,4,6,8)` 时 `a[0]` 读到 4、`a[1]` 读到野值）
⇒ 不是"固定偏一格"，更像基址/偏移里混进了一个**数据相关**的量。**未定位。**

**下一步的入口**：用"值即坐标"的画法（`ui_rect(a[i],0,20,14,…)`）逐下标对，
顺着"`a[3]` 对、`a[0..2]` 不对、且随元素值变"这三条事实往下查。

**回归**：`fib(n)` 那个例子（递归 + 函数 + 条件）实测无回归（`fib(10)` 画出 55 ✓）。

### 4.3 JavaScript —— 未知函数名被当成**变量**，调用成了间接跳转；且实参**正序压栈**

```
        move R1 var_ui_rect    ; 把 ui_rect 当成一个变量
        call R0                ; 间接调用 ⇒ 运行期跳到野地址
```
实参压栈顺序还是**书写顺序**（`10,10,80,40,色,1,0,0`），而包装读到的第一个参数是
**最后压的那个** ⇒ 即便调用成功，参数也全错。两处都要修。

### 4.4 C# —— 四条，全部已修（patch 0010，v0.96.190）；贪吃蛇跑通

① **全局变量读成了地址**（先修的那条）：`const int N = 5;` 实测画出 **1026** 个方块而不是 5 ——
   数据的读取用了 `OperandType.LABEL`，而 LABEL 是"标签的**地址**"⇒ `i < N` 变成
   `i < 地址(var_N)`。改成 `MEMORY`，并给**类字段**补上"登记数据段 + 折初值"。

② **带参方法的实参读反了**（"参数串槽"的真身）：序言里"把实参读进 R0"那句是
   `MOVE [R12+12+4i], R0`，而 `MOVE dest, src` 的 dest 在前 ⇒ 那是**把 R0 存进实参槽**。
   局部变量拿到的是"调用那一刻 R0 里恰好留着的值"= 调用点最后求值的那个实参。
   于是 `a1(x)` 侥幸对、`a2(x,y)` 的 y 变成 x（两个矩形**完全重叠**，"只看着一个"）、
   `a3(x,y,c)` 的 c 变成 x（近黑色，黑底上看不见）。
   ⚠ **"某个方法对、结构相同的另一个方法错"这种表象，第一反应不该是"槽互相踩"，
   而该去读生成的汇编** —— 这次读了才发现根本不是槽的问题。

③ **读数组元素永远读到数组头**：`SHL [#2,R0]`/`ADD [#4,R0]` 把**立即数当 dest ⇒ 结果被丢弃**
   （VM 只写 `dest.Type == REGISTER`），`ADD [R0,R1]` 又把和写进 R0，而下一句读 `[R1]`。
   写入路径同样三处（外加"保存值"那句 `MOVE R0, R2` 也是反的）。

④ **`static int[] sx = new int[N];` 从来没分配过**：类字段一律 `continue` 掉了，数组块
   整段没生成；而 `new int[N]` 的**长度在解析阶段就被丢弃**（返回空数组字面量），
   所以是"没分配 + 基址是 0"。配套的结构坑：入口 `main` **就是** `Main` 的标签，
   在它之前发的指令全是死代码（与 Swift 的 ① 同类）⇒ 字段数组的初始化改为在 `Main` 体内发。

**一条经验**：②③④ 的表象完全不同（参数错位 / 读到数组头 / 读到低内存垃圾），
根子只有两类 —— **操作数顺序写反**与**初始化没生成**。查它们唯一可靠的办法是
**把生成的汇编倒出来读**，不是换写法试。

### 4.5 Swift —— 三处已修（patch 0011）；贪吃蛇跑通

**① 已修（patch 0011）**：程序定义了 `func main()` 时，**顶层那段语句永远不会执行** ——
而全局变量/全局数组的初始化恰恰就在那段里（`var A = [...]` 生成的是"把数组基址存进 var_A"）
⇒ `var_A` 恒为 0 ⇒ 所有 `A[i]` 读写都落在地址 4/8/… 那片**低内存**上。
同一个函数内读写偏移一致所以"看着正常"，跨函数立刻露馅（`A[1] = 3` 读回来是别的值）。
修法**不搬指令、只挪标签**：入口仍旧指回顶层块，块尾 EXIT 前插一句 `call __user_main`。
⚠ 序列化器认的是**指令流里的 LABEL 伪指令**、不是编译器那张 `labels` 表 —— 只改表会白改一次
（第一版就是这样，出图一看才发现）。

**② 已修（同一条补丁）**：函数里的局部变量**漏进全局数据段**。`func count5() -> Int
{ var i = 0; var s = 0; while i < 5 {…} return s }` 实测返回 **3** 而不是 5；数据段里能看到
`var_i` / `var_k` / `var_tries` / `var_c` / `var_r` 这些**函数局部**。两条都不对：序言只给
**参数**留帧位、`GenerateVariableDecl` 无条件写数据段 ⇒ **同名局部在不同函数间互相踩**
（游戏里 `draw`/`step`/`occupied` 三处都有 `var_i`）。改法：序言递归预扫描函数体留帧位
（`ReserveLocals`）+ 声明处**栈帧优先**。验证：`i`/`s` 落到 `[R14-4]`/`[R14-8]`，
方块宽度**逐像素量**出来 40 = 5×8 ✓。

**③ 已修（同一条补丁）**：**读数组元素读回来的是字节偏移，不是元素值** ——
`GenerateIndexAccess` 最后一句 `MOVE [Mem("R1")], R0` 把 dest/src 写反了（`MOVE dest, src`），
于是"读"变成了"把偏移存进去"、R0 里留着的正是偏移。逐像素量出来的三个数
（`A[2]`→12 = 2*4+4、`A[16+k*2]`→92、`A[3]`→16 = 3*4+4）**全对得上偏移公式**。
改成 `MOVE R0, [R1]` 后，常量下标 / 变量下标 / 算术下标 / 动态写后读 = **24 / 24 / 32 / 56 像素**，
与期望逐一吻合 ✓。**这是"地址当值"那一族的第四次**（C# 的 LABEL/MEMORY、BASIC 的 `MOVE reg, R2`）。

**④ 最后一步（已定位并修掉）**：贪吃蛇当时能画出窗口 / 棋盘 / HUD / 食物 / **一节蛇身**，
而同一份状态在 `main` 里量是对的 ⇒ 状态没写错，是读取那一段的问题。见下条。

**⑤ 括号表达式恒等于 0 —— 三家前端同一个洞（v0.96.189 修）**

`GenerateExpression` 的 switch 里**没有 `ParenthesizedExpression` 分支**，落进
`default:` 被静默编成 `move R0 #0`。解析器明明建了这个节点
（`new ParenthesizedExpression(expr)`）、代码生成却没接 —— **Swift / C# / JavaScript 三家都是**
（15 个表达式类型里只漏了这一个；Java 接上了）。

**为什么查了四轮才找到**：症状是"`A[16 + (k) * 2]` 六次写入全落到同一个槽，
换纯常量下标 `A[16]…A[21]` 就全对"，看起来完全像"算式下标不能在多条语句里复用"——
而**真因是下标恒为 `16 + 0*2 = 16`**（`(k)` 折成 0），跟"复用"没有半点关系。
同一个洞还让 `draw()` 里的棋盘格 `(c + r) % 2 == 0` 从来没交替过（图元数 368 → 188，
差值 180 正好是 20×18 的一半，这条是修好之后的**独立佐证**）。

**判据**：不看现象猜，**读生成的汇编**（`vmlhost asm`）——修前 `(k)` 处就是 `move R0 #0`，
一步定位。这个手段前面几轮没用上，才绕了远路。

**修法**：补 `case ParenthesizedExpression paren:` 递归生成内层；类型推断同步补一条；
`default:` 从"静默发 0"改成**抛 `CodeGenerationException`** —— 这类"编译全绿、跑起来错"
的故障最该编不过（与 `DrawCommand.Vector` 定成必需成员同一个理由）。

**结果**：`Examples/swift/snake.swift` **跑通**，逐像素量：蛇头 316 像素（1 格）、
蛇身 632（2 格）、食物 316（1 格）—— 三个数全是精确整格。

**另外两条写法约束**（至今成立，与补丁无关）：模块级**标量**（`var n = 5`）读出来是垃圾
（与 C# 修之前同一个病）；`var w = ui_scr_w()` 直接喂给 `ui_win_open` 会开出 **60×64** 的小窗，
经一道局部变量才正常。**这两条不是偏好，是实测** —— 游戏里所有状态因此都放数组、常量都写成局部。

- 干净的部分：1/2/3 参方法的位置与取值都对；数组读写、返回值、全局数组写读（同一函数内）都对；
  定时器 + `ui_wait_msg` 的通路也通。
- 曾经坏的部分（都已修）：跨函数读全局数组读回偏移、函数局部漏进全局、括号恒等于 0。

#### 续 v0.96.195：**第 5 个参数起全是第 1 个参数的值**

写飞机空战时踩到的：一个 8 参的 `overlap(...)` 判相交**恒为真**（敌机一冒头就被打掉）。
原因在函数序言搬运"栈上那几个形参"的那一支，**两处错叠在一起**：

* **偏移少算 4 字节** —— Swift 的调用方是**把全部实参一个不落压栈**的（前 4 个另外再装进
  R0-R3），所以第 i 个实参在 `[R14 + 8 + 4*i]`；原式写成 `8 + (pi - 4) * 4`，
  仿佛"只有第 5 个起才在栈上"，而 `[R14+4]` 其实是 **CALL 自己压入的返回地址**。
* **操作数写反** —— 那一支是 `MOVE [栈槽], R0`，而 `MOVE dest, src` 的 dest 在前
  ⇒ 那是"把 R0 存回调用方的实参槽"，等于用最后压栈的值（= 第 1 个实参）把 4 个实参槽全冲掉。

⇒ 实测 `show(1,2,3,4, 200,150,7,9)` 里 bx/by/bw/bh **全是 1**；修完 **200 / 150 / 70 / 90** 逐个精确，
`overlap` 的两种情形也回到了 10（不相交）与 110（相交）。**"操作数写反"族第 9、10 次。**

⚠ 顺带记一条**验证方法**：这一条能被一眼看穿，是因为探针函数把每个参数**直接当矩形宽度画出来**——
「参数值」于是成了屏幕上能量出来的数。比"看画面对不对"可靠得多。
