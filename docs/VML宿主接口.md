# VML 宿主接口（手机端 syscall 500–599）

> ⚠ **方言说明**：本文里的汇编片段（`[R12+12]`、`[R14-4]` 等）用的是**旧的裸名写法**，
> VML 汇编现在要求寄存器一律带 `@`（**`[@R12+12]`**、`[@R14-4]`）。裸名**仍然能读**
> （老文本兼容），所以本文片段照旧成立；**新写的请带 `@`**。规范与新旧对照见
> [`third_party/vml/VML-README.md`](../third_party/vml/VML-README.md) 的「汇编语法：寄存器一律带 `@` 标记」。

> 这份文档是**手机端 VML 宿主接口的唯一存档**：号段约定、现有接口全表、设计约束、
> 以及"想做但还没做"的那批（含理由与优先级）。改接口先改这里，再改
> `WayCoder/UI/Shared/VmlUiProtocol.cs`（纯逻辑，四端共享）。
>
> 相关代码：`UI/Shared/VmlUiProtocol.cs`（协议层）、`WayCoder.Maui/Services/VmlUiCalls.cs`
> （宿主实现）、`WayCoder.Maui/Pages/DrawWindowPage.xaml.cs`（渲染与输入）。

## 1. 号段约定

| 项 | 值 |
|---|---|
| 保留号段 | **500–599**（运行时现用最大号是 402，见 `VMLRuntime/SyscallNumber.cs`） |
| 运行模式 | `mcu`（privilege > 0）。dispatch 顶部有 `UserAllowedSyscalls.Contains(n)` 这道门 |
| 白名单 | 宿主启动时 `VmlUiCalls.EnsureReservedSyscallsAllowed()` 把**整段**塞进 `SyscallConstants.UserAllowed`——它与运行时内部那份是**同一个对象引用**（`VMLRuntime.cs:179`） |
| 处理器 | `ISystemCallHandler`，**在内置 switch 之前**被调用（`VMLRuntime.Syscall.cs:23`）⇒ 这个号段完全由宿主解释 |

**两条结论**：
1. **加接口不需要改 `third_party/vml` 任何一行**——这是这个号段存在的全部意义。
2. 漏了白名单那一步的现象是「处理器明明注册了却永远不被调用」，而且不报错。

### 1.1 返回值与失败约定

- 寄存器 `R0` 是**返回值**；多数"动作类"接口返回 `0` 表示成功。
- **认不出的号必须返回 `false`（放行）**，否则会吞掉运行时的内置 syscall。
- 宿主内部出错**不能把 VM 打挂**：`VmlUiCalls` 统一 catch，记 `ErrorLog` 并回 `-1`。

#### `WIN_OPEN_EX`（#570，v0.96.233）—— 开窗时把两个声明一起给出来

```c
/* 棋盘必须竖着看，而且全程触摸落子（用不到手柄区） */
ui_win_open_ex("五子棋", w, h, VML_WIN_PORTRAIT, VML_WIN_NO_GAMEPAD);

/* 赛车：横版过关，要手柄 */
ui_win_open_ex("赛车", w, h, VML_WIN_LANDSCAPE, VML_WIN_NEED_GAMEPAD);

/* 画图表/放幻灯片：不要手柄区，画布吃满整屏，跟随旋转 */
ui_win_open_ex("报表", w, h, VML_WIN_ROTATABLE, VML_WIN_NO_GAMEPAD);
```

| 声明 | 值 | 含义 |
|---|---|---|
| `R3` 转屏 | `0` / `VML_WIN_PORTRAIT` | **只支持竖屏**（棋盘类）：屏幕锁在竖屏，怎么转都不动 |
| | `1` / `VML_WIN_ROTATABLE` | **支持旋转**（默认）：视口一变宿主就发 `WINDOWORIENT` + `WINDOWRESIZE`，并把**新的坐标空间**给到场景 |
| | `2` / `VML_WIN_LANDSCAPE` | **只支持横屏**（赛车 / 横版过关）：锁在横屏 |
| `R4` 手柄 | `1` / `VML_WIN_NEED_GAMEPAD` | 显示屏幕手柄区（**默认**） |
| | `0` / `VML_WIN_NO_GAMEPAD` | **整块手柄区连同折叠条一起不显示**，画布吃满整屏 |

⚠ **两个声明都在"开窗之前"生效**：`SCR_W/H` 报的可用绘图区随之变（不要手柄时就是整屏），
所以程序按它排的版**一开始就是对的** —— 不会"先按小画布排一次、再收到 resize 重排"。
实测五子棋改成 `PORTRAIT + NO_GAMEPAD` 之后画布从 `411.4×549.3` 变成 **`411.4×726.5`（吃满整页）**。

⚠ **只有 `ROTATABLE` 那一档会换坐标系**（见下表），这是故意的 —— 老程序见下。

⚠ **老程序不受影响**：`WIN_OPEN`（#520）语义一字不变（"跟随旋转、但**坐标系不动**"，宿主整幅缩放着显示）。
**没有把 #520 扩成 5 个参数**，是因为只传 3 个参数的程序 `R3/R4` 里是**它自己上一句留下的值**
（可能是个指针），宿主无从判断"这是不是真给了" —— 新能力一律走新号（与 `MSG_CLEAR` 当初一致）。

| 谁 | 转屏时窗口坐标系 | 为什么 |
|---|---|---|
| 老接口（没声明） | **不动**（整幅等比缩放着显示） | 它不处理 `WINDOWRESIZE`，换了空间会继续按老坐标画 ⇒ **内容被裁掉一大截** |
| `VML_WIN_ROTATABLE` | **换成新的可用绘图区** | 程序声明过"我会重排版"，按 `WINDOWRESIZE` 给的新尺寸重画即可 |
| `VML_WIN_PORTRAIT` / `LANDSCAPE` | 不适用（屏幕根本不会转） | 只有一种排版 ⇒ 与其让它处理第二种，不如不让它遇到 |

宿主侧对应 `WindowRotation` 的**四档**（Legacy / Follow / PortraitOnly / LandscapeOnly）——
两档模型（跟随 / 不跟随）会把老程序一起吃掉。

绘图是**保留模式**：程序只管往场景里追加图元，宿主按帧重绘。坐标单位是 **dp**（密度无关像素）。

#### `WIN_OPEN_PC`（#582，v0.96.353）—— **第三种窗口：电脑屏**（给老程序用）

三种窗口的分工：**主屏是命令行**（已有），**副屏才需要弹窗**，弹窗两种 ——
图形窗口（`#520`/`#570`，触摸 + 手柄）与**电脑屏窗口**（`#582`）。

```c
/* 老式 PC 程序：固定 640×480、要键盘、不要手柄、不锁方向 */
ui_win_open_pc("老程序", 640, 480, VML_WIN_ROTATABLE, VML_WIN_NEED_KEYBOARD);
```

与 `WIN_OPEN_EX` 的差别是**三件事**，全在 `VmlScene` 上表达：

| | 电脑屏 | 图形窗口 |
|---|---|---|
| 坐标系 | **固定**为程序声明的 `w×h`，**永不重排** | 自适应缩放，可跟随旋转 |
| 触摸 | **只发鼠标**（`Mouse*`，不发 `Touch*`） | 触摸 + 手柄 |
| 第 5 个参数 | **要屏幕键盘**（`VML_WIN_NEED_KEYBOARD`/`NO_KEYBOARD`） | 要手柄 |

⚠ **`R3` 在这里没有"支持旋转"那一档** —— 它只决定**锁不锁方向**
（`VML_WIN_PORTRAIT` 锁竖 / `VML_WIN_LANDSCAPE` 锁横 / 其它 = 不锁）。
坐标系永远固定：老程序按声明的分辨率排的版，换空间就会画到框外。

⚠ **种类由号决定，不是参数**（`VmlUi.KindOfWinOpen`）。没做成"一个号 + 种类参数"：
三种窗口的实现**根本不在同一层**（图形 = 开页 + 场景；电脑屏 = 固定坐标系 +
不同输入 + 键盘），用一个号绑住三者等于把"分类"永久写进跨语言契约。
也**没有**给 `#570` 的 R3 加一档 —— R3 是转屏声明，加档就是给同一只寄存器第二语义。

画图照旧走 `ui_*`（**不碰显存** —— 显存/BGI 那一整套已定案不做，见
[`老程序兼容性.md`](老程序兼容性.md) 第七节）。

#### 电脑屏窗口的键盘（v0.96.357）

老程序的输入就是键盘，所以电脑屏窗口有**两条**键盘路，各管各的：

| 来源 | 路径 | 什么时候用 |
|---|---|---|
| **屏幕键盘**（页面画出来的 81 个键） | 按钮 → `PostKeyDown/Up` → `VML_MSG_KEYDOWN/KEYUP` | 手机没外设时的兜底 |
| **外接物理键盘** | `Activity.DispatchKeyEvent` → `Services/HardwareKeys` → 同一条消息 | 正经用法（蓝牙键盘） |

**两条都发 `VML_MSG_*` 消息，一条都不走 `getch()` 那条命令行输入队列。** 这是刻意的：
两类窗口对应**两条输入路径** —— curses/conio 那类老程序跑在**命令行页**（输入走
`ShellPage` 的按键队列 → `MauiVml.ReadChar`），而调 `ui_win_open_pc` 的程序**自己有窗口**，
输入就是窗口消息，与手柄同一条路。把窗口上的键投进命令行页的队列是"按了没反应"最常见的错法。

**键码一律照 Win32 虚拟键码**（`VmlKeys` 是唯一真源）—— 程序里写 `key == VML_KEY_F1`，
在手机上按屏幕键与在 PC 上按真 F1 必须得到同一个数，否则同一份老程序要写两套判断。
标点也照**物理键**归位（`!` 归 `VK_1`、`{` 归 `VK_OEM_4`），因为 Win32 程序查的是
"物理键 + Shift 状态"，而不是那个字符本身（`VK_SHIFT` 会单独发出去）。

⚠ **键盘占自己的一行，不盖在画布上**（与手柄区同一种做法：chrome 让画布变小，
而不是压在画布上面）。老程序的状态行、命令行、提示语都画在**底部**，
被压住就是"这个程序用不了"—— 第一版做成浮层，真机上 `pcscreen.c` 的 `KEY`/`MOUSE`
两行当场看不见。收起键盘（那行是 `Auto`）⇒ 高度塌成 0，画布立刻吃回来。

⚠ **只有 Android 接了物理键盘**（`DispatchKeyEvent`；命令行页那条走 `View.KeyPress`）。
iOS/MacCatalyst/Windows 还没接。

| 539 | `DRAW_CIRCLE_GRAD` | R0..R2=cx cy r R3=渐变id\* | 0 |

**574–576 是「一个号 + 操作码」**，与前面"一个功能一个号"的写法**刻意不同**：

> VML 程序**不直接调 syscall** —— 它调 `Lib/` 里的包装函数（`ui_draw_star` 之类），
> 22 门语言各有 GenLib 生成的绑定。**号是给库用的，不是给程序作者用的**，
> 所以一个号完全可以承担多个"版本"。于是**加形状再也不用占号**（加一个形状码 + 一行 C 包装），
> 参数个数也回到"通用槽固定 7 个"，避开"星形要 9 个参数"这个全仓没有先例的形态。

形状码（`DRAW_SHAPE` 的 R0，跨语言契约 **只能末尾追加**）：

| 码 | 形状 | R1.. 的含义 |
|---|---|---|
| 0 | 矩形 | x y w h 半径 |
| 1 / 2 | 圆 / 椭圆 | cx cy r ／ cx cy rx ry |
| 3 | 直线 | x1 y1 x2 y2 |
| 4 / 5 | 多边形 / 折线 | 点数组\* 点数 |
| 6 / 7 | 路径 / 文字 | d\* ／ x y 文本\* |
| 8 / 9 | 星形 / 正多边形 | cx cy 外半径 内半径 角数 旋转角 ／ cx cy 半径 边数 旋转角 |
| 10 / 11 | 圆环 / 扇形 | cx cy 外半径 内半径 ／ cx cy 半径 起角 终角 |
| 12 | 心形 | cx cy 尺寸 |
| 13 | **椭圆渐变** | cx cy rx ry 渐变名\*（唯一自带刷子的码，为与 `ui_rect_grad` 同形） |

**样式取自当前状态**（`SET_STYLE`）：填充刷子 / 画笔（刷子+线宽+线帽+虚线+箭头）/ 文字刷子。
"颜色 = 只有一个色标的刷子"，所以 `SET_STYLE` 的 R1 **直接传颜色也合法**
（句柄是小整数 1..128，颜色 ≥ 0x01000000，两者值域不重叠）。

⚠ **本批画笔与文字只支持纯色** —— 渐变描边 / 渐变文字要等引擎侧把"可采样描边"与
"渐变文字"做出来（DSL 与三条后端都要动）。给渐变句柄时宿主**记一次警告并退回它的起始色**，不静默。

**三条约定，写代码前先看一眼**：

1. **渐变几何是"千分之一"的整数**（0..1000），进 DSL 前在 `VmlScene.AddGradient` **一处**换算成
   归一化 0..1。传 0,0,1000,0 是"从左到右"（默认），径向给 cx,cy,r（第 4 个忽略）。
   单位只在那一处换算 —— 两端各算一次就是"沉默的错"（方向向量变成 1000 倍长，
   `t` 恒为 0 ⇒ 整块只剩色 A，看起来像"渐变没生效"）。实测踩过一次。

   ⚠ **归一化是"相对被填充形状自己的包围盒"，不是相对整幅画布**（= SVG 的 `objectBoundingBox`；
   `1000` 就是**形状自己**的右边缘，不是画布的右边缘）。同一个渐变套在大矩形上是"从左到右"，
   套在小方块上也是"从左到右"（而不是"整幅渐变的一小段"）。
   三处实现都按这条：光栅 `FillTransformed` 的 `nx = (lx - minX) / spanX`（局部包围盒）、
   SVG 导出的 `objectBoundingBox`、平台刷子（MAUI 的 `SetFillPaint(paint, rect)` 要的正是
   "相对 rect 的 0..1"，**原样透传即可、不要换算**）。
   **这条写清楚是有代价换来的**：v0.96.182 之前这里只写"归一化 0..1"、没写"相对谁"，
   于是矢量后端把"场景归一化"又换算了一层，渐变在小形状上变成一段切片 —— 数看着对、
   语义是错的。**读到"归一化"先问一句"相对谁"。**
2. **点数组是内存里的 int32 `x,y` 对**，`R1` 给的是**点数**（不是 int 个数）。上限
   `VmlUi.MaxPolyPoints` = 512（越界就地停，不读坏内存）。
3. **路径用 SVG 语法**（`M L H V C S Q T A Z`，大小写区分绝对/相对）。光栅化那侧现在会
   **展平曲线**（`Infra/DrawPath.cs`），与导出 SVG 形状一致；在此之前曲线段是被静默丢掉的
   （只认 `M`/`L`/`Z`），也就是"同一份 DSL 导出 PNG 与导出 SVG 图形不一样"。
   多个子路径之间按**奇偶规则**挖洞（`M…Z M…Z` 画圆环）。

#### 绘窗有两条后端：矢量（默认）与光栅（回退）

`ui_present()` 之后窗口怎么把这一帧落到屏幕上，宿主有两条路（v0.96.180 起默认走矢量）：

| | 矢量（默认） | 光栅（回退） |
|---|---|---|
| 做法 | 图元直接画到平台画布（MAUI `ICanvas`），光栅化交给 GPU | 手搓光栅化 → PNG 编码 → UI 线程解码 → 贴图 |
| 每帧代价 | **≈1ms**（真机实测：解析 0.8 + 平台绘制） | ≈80ms（后台 26 + UI 54，且每帧新建一张位图） |
| 抗锯齿 | 平台做（比 3× 超采样更好） | 3× 超采样再盒式降采样 |
| 文字 | 平台字体 | 手搓 TrueType 光栅化 |

**一致的部分才是关键**：几何与画法规则是**同一份**（`DrawGeo` 出点集，`DrawCommand` 两个画法共用），
坐标与触摸反算也共用同一个 AspectFit 结果 —— 两条后端不会各算一套。

**写程序时要知道的三条**：

1. **文字基线**：DSL 里 `y` 是**基线**；矢量后端用平台字体、按「基线 − 0.8×字号」换算，
   度量与手搓字体不完全相同 ⇒ 同一段文字在两条后端上可能有 1~2px 的垂直差（不影响布局，只影响观感）。
   ⚠ 2026-09-23 修正：**光栅那条路原先把 `y` 当顶线**（`TrueTypeFont.Render(yTop)`），
   与上面这条契约相反 ⇒ 桌面 PNG 的文字比手机整体低 0.8×字号，而"桌面看着对、上手机才发现"
   是最贵的一类故障。现已统一到基线（光栅侧减一个上升，比例取共享常量 `DrawParse.TextAscentRatio`）。
   同时把**竖对齐**做成了四档 + 状态式（见下）。

   **竖对齐四档**（`ui_set_valign` #586 设一次，之后 `ui_text_cur` 都用它；也可逐次传
   `ui_text_v` 的 `valign` 参数）：

   | 档 | 常量 | 含义 |
   |---|---|---|
   | 0 | `VML_VANCHOR_BASE` | **`y` 就是基线** —— **默认**，也是老行为（手机端一直如此渲染） |
   | 1 | `VML_VANCHOR_MIDDLE` | 盒竖直中心落在 `y`（"在方框/圆里居中"用这一档） |
   | 2 | `VML_VANCHOR_BOTTOM` | 盒底落在 `y` |
   | 3 | `VML_VANCHOR_TOP` | 盒顶落在 `y`（与基线相差一个"上升"，≈0.8×字号） |

   ⚠ **0 专门留给老行为**：任何不设竖对齐的程序，渲染逐字不变（改 0 的含义＝悄悄挪动所有既有程序的文字）。
   所以"顶"是 3 而不是 0 —— 名字看着别扭，但那是有意的。
   ⚠ **状态跟随窗口**：字体属性 / 竖对齐 / 默认色 / 画图参数都挂在**场景**上，
   开窗建场景、关窗销毁 ⇒ 新窗口自然回到默认值，不跨窗口残留。
2. **虚线相位**从路径起点算（光栅侧是逐段画），很长的折线上可能差半个周期。
3. **画不了的图元会让整个窗口回退光栅**（慢一个数量级）：目前是"带旋转/错切的贴图"。
   插件的自定义绘图指令想留在矢量后端，就得实现 `IDrawCommand.Vector` ——
   它是**必需成员**，不实现连编都编不过（故意的：静默少画东西比编不过难查得多）。

#### `SCREENSHOT`（#588，v0.96.409）—— 程序自己主动截屏

把**本 App 窗口**截成 PNG 写进程序给的路径。与上面四个的区别：那几个读的是**画布场景**
（程序自己画了什么），这一个读的是**平台窗口** —— 屏幕手柄、标题栏、弹框都在里面，

```c
n = ui_screenshot("shot.png");   /* → 写入字节数；-1 = 失败 */

```

| 平台 | 截的是什么 |
|---|---|
| Android | Activity 的 `DecorView` 画进 Bitmap（`GetPixels` → RGBA） |
| iOS / MacCatalyst | 窗口 `CALayer` 渲染进 `CGBitmapContext` |
| Windows | WinUI `RenderTargetBitmap`（BGRA → RGBA 换序） |
| **桌面脚手架** | **没有 App 窗口 ⇒ 退化为光栅化 VML 场景** |

1. **不是整屏截屏** —— 拿不到状态栏与其他 App。整屏在 Android 要 `MediaProjection`
   （弹系统授权框、用户可拒、还要前台服务），iOS 基本做不到；截自己的窗口四端都**无权限**。

2. **-1 不区分原因**（路径非法 / 这一端截不了 / 写不进去）—— 程序该做的事一样。
   真正的原因进宿主日志。**桌面与手机截出来的内容不一样**（见上表最后一行），这是有意的。
3. **路径是相对沙箱的**：空串 → `shot.png`，无扩展名自动补 `.png`。
   含 `..`/`.` 段或盘符/scheme 的**直接 -1 且一个字节都不落盘** ——
   这道清洗（`VmlUi.SanitizeShotPath`）是**防逃逸的唯一屏障**，因为两端宿主的
   `ResolvePath` 都不做沙箱钳制。（绝对路径是**剥掉首部分隔符**、不是拒绝，
   与 `SandboxPath` 同口径；剥完仍是相对路径，逃逸不了。）

#### `SCR_ORIENT`（#569，v0.96.230）

程序要**按方向换排版**（棋盘放左/放上、信息面板横排/竖排、格子尺寸）时问它。
**开窗之前就能问**；运行中方向变了，宿主会发 `WINDOWRESIZE`（`A`=新宽 `B`=新高），
收到后**重新问一次本号**再重排版。

```c
int land = ui_orientation();          /* 0 竖屏 / 1 横屏；C 头文件里是 VML_ORIENT_* */
int w = ui_scr_w(), h = ui_scr_h();
ui_win_open("我的游戏", w, h);
```

⚠ **别拿 `ui_scr_w() > ui_scr_h()` 去推方向。** 那两个数报的是**可用绘图区**
（实测横屏 396×301、竖屏 411×525），形状确实跟着方向走，但它是宿主**排版算出来的**二手信息 ——
手柄收起/展开、页面留白、以后再加什么 chrome 都会动它。**方向是设备本身的属性**：
宿主取 `DeviceDisplay` 的真实宽高判定，取不到才退回按实测视口推（真机上走不到那一步）。

### 全能接口 `CALLJSON`（#573，v0.96.234）—— 加功能不用占号

```c
char buf[256];
ui_call_json("screen", "", buf, 256);              /* {"ok":true,"result":{"w":395,…}} */
ui_call_json("echo", "{\"n\":7}", buf, 256);        /* 参数原样回来，自检/调试用 */
```

| 号 | 名称 | 入参 | 返回 |
|---|---|---|---|
| **573** | **`CALLJSON`** | R0=函数名\* R1=参数 JSON\* R2=输出缓冲 R3=缓冲容量 | 写入字节数（不含结尾 NUL），失败 -1 |

结果**写进调用方给的缓冲区**（与 `DLG_INPUT` 返回文本同一套 —— VM 里没有宿主能"交还"的堆）。
返回值永远是对象：

```json
{"ok": true,  "result": <该函数返回的任意 JSON>}
{"ok": false, "error": "未知函数: xxx"}
```

**这个号存在的理由**：每加一个能力就占一个 syscall 号、加一对 C 包装、重生成 22 种语言的绑定 ——
对**不要求性能**的功能（查版本、报屏幕、读偏好…）太重了。有了它，
**加一个能力 = 宿主侧注册一行**：

```csharp
VmlJsonApi.Register("screen", _ => JNode.Object().Set("w", 395).Set("h", 652));
```

| 已注册 | 参数 | 结果 |
|---|---|---|
| `echo` | 任意 | 参数原样返回（**管线自检 + 程序调试口**） |
| `version` | — | `{app, cn, version, platform}` |
| `screen` | — | `{w, h, orientation, landscape}` —— 与 `SCR_W/H/SCR_ORIENT` **同源** |

⚠ **性能敏感的调用不要走这里**：一次调用要序列化 + 解析两趟 JSON，再穿一次"写进 VM 内存"的拷贝。
绘图、输入这类每帧/每个事件都发生的调用仍然走专用号。

⚠ **实现抛异常不会把 VM 打挂**：异常在 `VmlJsonApi.Invoke` 里被接住、翻成 `ok:false` 交给程序 ——
与宿主 syscall 处理器那条"出错记日志并回失败码"的约定一致。这条有自测钉着。

⚠ **缓冲区装不下**时，写回去的是一段**说明原因的信封**（能放下的话），返回 -1 ——
不让程序拿到一段被截断的、解析不出来的 JSON 还以为是自己的问题。

**拿不到缓冲区指针的前端**（Python / BASIC / Lua…）用三个薄封装：
`ui_call_json_s(fn, args)` → 结果进静态缓冲（4KB），再用 `ui_call_json_len()` / `ui_call_json_at(i)`
按字节读 —— 连 `char*` 都不用解引用。

### 通用宿主调用口 `CALLWITH*`（#577–580，v0.96.326）—— 加功能不用占号，且**零编解码**

```c
int v[8];
v[0] = VML_CALL_ECHO_INT;          /* ① 调用号（下面有宏） */
v[1] = 1; v[2] = 2; v[3] = 3;      /* ② 参数，不够的位留 0 */
int r = callwithint8(v);           /* ③ 返回值**覆盖 v[0]** —— ④ 拿不到原来的 v[0] */
```

| 号 | C 包装 | 值怎么进 | 返回写回 |
|---|---|---|---|
| **577** | `callwithint8(int* v)` | v[0..7] → **R0–R7** | **R0** |
| **578** | `callwithfloat8(float* v)` | v[0..7] → **F0–F7** | **F0**（+ R0 位置镜像） |
| **579** | `callwithlong4(long* v)` | v[0..3] → **L0–L3** | **L0**（+ R0 低 32 位镜像） |
| **580** | `callwithdouble4(double* v)` | v[0..3] → **D0–D3** | **D0**（+ R0 低位镜像） |

**第 0 个槽既是调用号（进）又是返回值（出）**，所以"调用方拿不到 `v[0]`"是 ABI 的一部分，不是缺陷。
四个口的调用号都由 `(int)v[0]` 得到 —— 所以 `F0`/`L0`/`D0` 里那个调用号**也必须能被 `float`/`long`/`double`
精确表示**（id 取小整数即可，`< 2²⁴` 绝对安全）。

#### 为什么与 `CALLJSON` 并存（两条路各管一半）

| | `CALLJSON`（#573） | `CALLWITH*`（#577–580） |
|---|---|---|
| 加一个能力 | 宿主注册一行 | 宿主注册一行 |
| 每次调用的代价 | 两趟 JSON 编解码 + 一次内存拷贝 | **零编解码**（参数就在寄存器里） |
| 调用形态 | `ui_call_json("名", "{…}", buf, cap)` | `callwithint8(v)` |
| 类型 | 运行时才知道（JSON） | **写死在调用口上**（int/float/long/double） |
| 适合 | 版本、屏幕、偏好这类**偶尔**调的 | 每帧/每个事件都要调的 |

按仓里那条老规矩（`DRAW_SHAPE` 的"一个号也能封装多个版本"），**本想合成一个号**加一个"类型"参数，
但类型的差别**宿主从寄存器内容上看不出来**（`R0` 里放 `1` 还是 `1.0f` 的位模式，值本身说不出），
而额外加一个类型参数要挤掉一个本来就不够用的参数槽 —— 所以四个号，各带各的类型。

#### 调用号（id）—— 跨语言契约，只能末尾追加

C 宏在 `Lib/c/waycoder_ui.h`，C# 常量在 `VmlCallRegistry.VmlCallIds`，**两边同值**：

| id | 种类 | 语义 |
|---|---|---|
| 1 | int8 | `ECHO_INT`：7 个参数的**位权拼接**（`a₁ + a₂×10 + … + a₇×10⁶`）—— 传 `1..7` 得 `7654321`，哪个参数没到、串没串位一眼看得出来 |
| 2 | float8 | `ECHO_FLOAT`：同上，浮点域 |
| 3 | long4 | `ECHO_LONG`：`a₁ + a₂×1000 + a₃×10⁶` |
| 4 | double4 | `ECHO_DOUBLE`：同上，浮点域 |
| 5 | int8 | `HOST_INFO`：宿主种类（**1=桌面脚手架 / 2=手机 App**） |

这一族既是**模板**（照抄它加一个能力只要一行 `RegisterInt8(id, a => …)`），也是**自检口**。

#### 失败长什么样

**不崩**。没注册过的 id、种类对不上、实现体自己抛异常，都写回一个**负数失败码**
（取值与 `VMLRuntime/ErrorCodes.cs` 同值，正数才是正常返回值）：

| 码 | 含义 | 自测 |
|---|---|---|
| `-2` | 参数非法（调用号是负数、或种类与注册的不符） | ✅ |
| `-6` | 没有注册这个调用号 | ✅ |
| `-9` | 宿主内部错误（实现体抛了异常，已被接住） | ✅ |

宿主同时会记一条可读日志（手机 → `ErrorLog`、桌面 → stderr），例如
`[VMLCALL] #577 id=9999 调用失败：没有注册这个调用号：9999（Int8）`。

#### 实现在哪（三处，缺一不可）

| 层 | 位置 | 说明 |
|---|---|---|
| 注册表 + 寄存器↔参数 + 失败码 | `WayCoder/UI/Shared/VmlCallRegistry.cs` | **两端共用一份**（手机 / 桌面 CLI 都编译它） |
| 宿主 | `WayCoder.Maui/Services/VmlUiCalls.cs`、`scripts/vmlcli/Program.cs` | 各把 VM 的四组寄存器喂进去（`TryHandle`） |
| C 包装 | `Lib/shared/src/vmlui.c` + `Lib/c/waycoder_ui.h` | 把数组装进寄存器、发 syscall |

⚠ **宿主只拿得到 `int[] registers`**（`ISystemCallHandler` 的参数就是它，只有 32 位），
所以 `float8`/`long4`/`double4` 的参数**必须从运行时实例上取** `FloatRegisters` /
`LongRegisters` / `DoubleRegisters` —— 两个宿主都在建完 VM 之后回填了一个 `Vm` 引用。
光看 `int[] registers` 只能拿到低半截（`SetLongValue`/`SetDoubleValue` 只镜像低 32 位）。

#### 端到端验证（2026-09-20，桌面 `scripts/vmlcli`）

```
int8      = 7654321
float8    = 1234567          ← F0..F7 真的到了（7,6,5,4,3,2,1 的位权拼接）
long4     = 3002001          ← L0..L3
double4   = 3002001          ← D0..D3
未注册    = -6
类型不符  = -2
负数号    = -2
宿主      = 1
```

⚠ **三个前端缺陷**（已复现，属 `VMLPrepares/CCompiler`，不是这四个口的问题）—— 写 C 程序时会撞上：

1. **`float[]` / `double[]` 数组元素的"存"到不了内存**（标量正常）：
   `float v[8]; v[1] = 7.0;` 之后内存里那 4 个字节是 0。所以端到端验证是**用 `int[]` 摆出位模式**
   再把它当 `float*`/`double*` 传进去做的（`Examples/c/callports.c` 就是这么写的）。
2. **全局 `long` / `double` 标量按 32 位存**（截断）；局部标量正常。
3. **同一个 `long[]` 数组连续存多个元素会丢**（实测 4 条只有前 2 条落地）。

### 2.1 消息模型（固定 16 字节）

程序按 4 个 int 读：`[0]=类型 [1]=A [2]=B [3]=时间戳毫秒`。
定长布局是为了让**任何语言的 VML 前端**都能直接读（C 用 struct、BASIC 用 PEEK），不依赖宿主序列化。

| 类型 | 值 | A | B |
|---|---|---|---|
| `None` | 0 | — | — |
| `KeyDown` / `KeyUp` | 1 / 2 | 键码（Win32 虚拟键值，见 `VmlKeys`） | 0 |
| `MouseMove` / `MouseDown` / `MouseUp` | 3 / 4 / 5 | 场景 x | 场景 y |
| `TouchDown` / `TouchMove` / `TouchUp` | 6 / 7 / 8 | 场景 x | 场景 y |
| `Timer` | 9 | 定时器 id | 装机时的用户标记 |
| `WindowClose` | 10 | 0 | 0 |
| `WindowResize` | 11 | 新宽 | 新高 |
| `WindowOrient` | 12 | 新方向（0 竖屏 / 1 横屏） | 0（预留） |

**「屏幕变了」是两条消息，不是一条**：`WindowResize` 说"你能画多大"，
`WindowOrient` 说"机器横着还是竖着拿"。程序按后者决定**怎么分栏**（棋盘放左还是放上、
信息面板横排还是竖排），按前者决定**格子算多大** —— 两件事，少一条就只能让程序
从尺寸里猜方向，而画布形状是宿主**排版算出来**的二手信息（手柄收起/展开都会动它）。
宿主**先发方向、后发尺寸**（同一个 tick）：程序处理尺寸那条时读到的方向已经是对的。

#### ⚠ `ui_wait(msg, timeout)` 的 `timeout = 0` 是「**无限等**」，不是「不阻塞」

宿主实现是 `Take(0) → _signal.Wait(Timeout.Infinite)`。想"看一眼有没有消息、没有就接着干"
必须用 **`ui_poll(msg)`**（它是非阻塞的 `TryTake`）。

**这条踩过一次**（v0.96.178 量帧率时）：探针写 `ui_wait(msg, 0)` 想连续出帧，结果每轮都在
等下一秒的定时器消息，量出来的"帧率"其实是定时器频率（1 fps），白白绕了一圈。
游戏该用哪个看主循环的形状：

- **事件驱动**（常态、省电）：`ui_wait(msg, 0)` 阻塞等消息，醒来再按需重画 —— 两个游戏都是这样，
  所以它们跑着的时候 CPU 只有 ~20%；
- **连续动画**（每帧都要重画）：`ui_poll(msg)` + 画 + `ui_present()`，
  但这样是**满负荷空转**（VM 会尽力跑），移动端要自己按帧率节流。

## 4. 设计约束（踩过的坑，别重犯）

1. **消息固定 16 字节**，加字段=打断所有现有程序。要加就加**新的轮询接口**。
2. **字符串一律 UTF-8、NUL 结尾、按地址读**。越界/非法读一律返回空串，不抛
   （`VmlUiCalls.Str`）。
3. **宿主侧要钳参数**：字号、音量、时长、频率都要 clamp——传 0 或负数会让下游算出零/负值，
   症状是"画不出来"或"程序卡住"，很难查。
4. **别在宿主里长耗时**：syscall 是在 VM 线程上同步返回的，任何阻塞都会拖住整个程序。
   要等用户的（弹框）例外——那正是"程序在等人"的语义。
5. **音频别用 `ToneGenerator` 做叠加**：它同时只能一个音。要多个音效同时响得用 `AudioTrack`
   自己混（当前 `AUDIO_TONE` 是单通道，够用且简单）。
6. **`WindowResize` 曾经是"协议里有、宿主从不发"的死消息**。转屏、折叠屏、以及绘图页新增的
   **手柄折叠条**都会改视口，程序却一无所知。现在在实测视口变化时补发（见
   `DrawWindowPage.PublishViewport`）——**光有协议不叫有接口，得有人发**。
   `WindowOrient`（#12）与 `SCR_ORIENT`（#569）同批加：**主动查**与**被动收**都要有，
   两条路的判据必须同源（`VmlUiCalls.ScreenOrientation`），否则"查到的"和"收到的"
   会在某个边界上不一致。
   ⚠ 两条消息都**只在"已经有过旧值"之后才发**：程序刚开窗那一下它自己问过、也按那个值排好版了，
   再补发一条只会让它白排一次。
   ⚠ 上报跑在 `DrawWindowPage` 的 **40ms 定时器**里，**不能放 `OnSizeAllocated`** ——
   那是布局期回调，转屏时会被夹在"页面已变矮、新布局还没换上去"的中间态里调一次，
   量到的是几十 dp 的畸形尺寸（实测 545×46），记进 `MeasuredViewport` 会让**下一局游戏**
   照它开窗。
7. **持久化要带前缀**：`STORE_*` 走宿主 Preferences，键统一加 `vml.` 前缀，免得和 App 自己的
   配置打架。

## 5. 加一个新接口的步骤

1. 在 `UI/Shared/VmlUiProtocol.cs` 的 `VmlUi` 里加号 + 文档注释（含入参/返回/钳位规则）；
   纯逻辑的部分（解析、钳位、格式化）也放这里，**这样能被主工程自测覆盖**。
2. 在 `WayCoder.Maui/Services/VmlUiCalls.cs` 的 `HandleSyscall` switch 里加分支，
   实现体写成小方法（弹框/绘图各自成组）。
3. 号段白名单**不用动**（`ReservedRange()` 覆盖整段 500–599）。
4. 需要权限的在 `Platforms/Android/AndroidManifest.xml` 里声明（见 §6）。
5. 想要 VML 侧好用的包装函数：**C 源写 `Lib/shared/src/*.c`、声明写 `Lib/c/waycoder_ui.h`，
   然后用 GenLib 重新生成**（`dotnet run --project third_party/vml/tools/GenLib -- -b` 编译，
   `-m` 生成 22 种语言的模块包装，`-g` 生成源文件绑定）。
   ⚠ **`.vml` 是生成物，永远不要手改**（改了会被下一次 GenLib 冲掉，且打断 thunk 链）。
   ⚠ `third_party/vml` 自 2026-09-17 **已与上游分家**（见 `third_party/vml/FORK.md`），
   `sync.sh` 已删除 —— 直接改就是最终状态，**不必再做成补丁、也不必提给上游**。
   （v0.96.173 时期"改了会被 rsync 冲掉、得提上游"那条已经作废。）
   C 语言也可以直接 `SYSCALL #566` 调保留号，但**能走包装就走包装**（见第 7 条）。
6. **真机验证**：新建的接口在桌面上测不出来（没有震动/音频设备），必须装 APK 实跑。
7. **别用 C 内联汇编直连多参数 syscall**（v0.96.173 实测）：
   `asm("MOVE R0 ${freq}"); asm("MOVE R1 ${ms}");` 生成的是
   `move R0 [R12+12]; move R0 R0; move R0 [R12+16]; move R1 R0` —— **`${}` 展开时总是先载入 R0**，
   第二个参数把第一个覆盖掉。多参数一律走 `Lib/` 里的包装函数。
8. **带缓冲区的接口（`STORE_GET` 这类）在 C 里有两条既有前端缺陷**（v0.96.173 实测，见 §8）：
   缓冲区放全局、读回用 `atoi`/`strcmp`。

## 8. C 侧使用带缓冲区的接口：一个已修的前端缺陷 + 一条判定纪律（v0.96.173~174）

`ui_store_get(key, buf, cap)` 把字符串写进调用方给的缓冲区。当时的现象是「**长度对、内容不对**」，
一路查下来是一条**既有**的 C 前端缺陷，已在本地修掉并补成第 4 个 patch：

| 现象 | 真因 | 状态 |
|---|---|---|
| **全局 `char` / `short` 数组用下标访问按 32 位读写** | `InferExpressionType(ArrayAccess)` 只查 `variableTypes`（**只装局部变量**），全局数组查不到就退化成 `ExprType.Int` ⇒ 走 `MOVE` 而不是 `MOVEB` | ✅ 已修：`patches/0004-c-global-array-elem-type.patch`（复现 `.scratch/vmlhost/tests/globchar.c`） |

**局部数组一直是对的**（`variableTypes` 里有），所以这个坑只在全局数组上冒头 —— 而这一点很要命：
第一版结论把症状误判成了「**局部数组的地址传给函数是错的**」，于是写下了"缓冲区必须放全局"这条
并不存在的规矩。**教训是判定方法**：那一版用 `puts` 当判据，而本环境的 `puts` 在字符串字面量
较多的程序里输出会**串行/重复**（补丁前后一个样，是另一件事），于是把「stdio 坏了」看成了
「codegen 坏了」。**改判定不经过 stdio**（每条结论用一个 `ui_beep` 频率报出来，宿主原样打印）
之后，六个格子一次就量清了：局部下标读写 ✓✓、全局下标读写 ✗✗。

所以现在写 `ui_store_*` 的用法**不需要任何规避**：缓冲区放哪都行、`buf[0]` 也能直接读。
`Examples/c/tetris.c` 里那份（全局 `hibuf` + `atoi`）照旧能用，只是不必再当成硬约束。

> ⚠ **写桌面验证程序的两条纪律**（都是这次踩出来的）：
> ① **别拿 `puts` / `printf` 的输出当判据** —— 本环境里 `printf` 的格式化路径会崩
>    （`MOVEB @2, R0`，地址是垃圾值），`puts` 在部分程序里输出会串行/重复。
>    正解是**不经过 stdio 的判定**：一条结论一个 `ui_beep` 频率，宿主原样打印；
>    `ui_dlg_msg` 是"宿主从内存里读到的字符串"的现成探针（标题/正文都会被读出来）。
> ② **A==C 只证明"两条执行路径逐字节一致"，不证明逻辑正确** —— 有"两边一样地错"这种情形
>    （实测有：调用方的局部数组会被后续库调用踩坏，两条路径踩得一模一样）。
>    要看逻辑对不对，得靠出帧看画面。
>
> ⚠ **写用到 `Lib/` 函数的 C 程序时，先读这一段**（v0.96.175 查到根）：`Lib/` 里的函数
> **两套栈清理约定并存** —— 446 个"调用方清参数"（与 C 前端生成的一致）、**764 个"被调用方
> 自己清"**。C 前端每条调用后都会自己 `add R13 #N`，所以每调一次那 764 个之一，**栈指针就
> 多释放一次**（`strlen` 一次多 4 字节）。漂了之后，凡是**用 `pop` 取临时值**的地方都会读错：
> 实参槽、数组下标的中间量都在此列 ⇒ **静默算错**，表现是"同一段代码有时对有时错"。
>
> - 只用 `waycoder_ui.h` 的包装函数（它们是"调用方清"，与前端一致）→ 不受影响。
>   `Examples/c/tetris.c`、`gomoku.c` 都属这一类，实测正常。
> - 用到 `strlen`/`strcmp`/`printf`/`atoi` 这些，**且中间夹着别的调用或数组下标运算** → 会错。
> - 正解是**用当前前端把 `Lib/` 重新生成一遍**（全库统一到"调用方清"），那是上游 VML 仓库的事；
>   `Lib/` 由 `sync.sh` 同步，本地改会被冲掉，所以这里只诊断、不改。
> - 最小复现 `.scratch/dup_a.c`（`ui_beep(10000 + strlen(loc), 1)` 实测报 `6`，应 `10005`）。
>
> 三条**仍已复现未定因**（细节见 CHANGELOG v0.96.174/175）：带三元表达式的实参可能传错、
> `puts` 输出串行、`printf` 崩溃 —— 后两条多半就是上面这条的后果。

## 9. 命令行那条路：终端**输入/输出**契约（v0.96.351/352）

上面 §2 那批号是**绘图窗口**的（保留模式、`ui_*`）。**命令行窗**走的是另一条路 ——
程序的 `putchar`/`getchar`（`#4`/`#5`）经宿主直接上屏/取键，**一个 syscall 号都不占**。
它有自己的契约，做新功能（尤其**第三种"电脑屏"窗口**）时要照同一套走。

### 9.1 输出：**边跑边出**，网格是"替换那一块"

    程序 putchar → CaptureIo 攒 → **输出泵**（80ms / 16KB 节流）→ ShellStream → 命令行页

- `ShellStream` 判这段输出是**线性**（往下堆，**追加**）还是**全屏**（一屏一屏画，**替换那一块**）
- **呈现方式一旦定下就不可逆** ⇒ 探测期**攒着不出**，判定了再一次性决定
  （所以不需要"已 append 的文本怎么撤回"那套逻辑）
- ⚠ 判定**必须能区分"确定不是全屏"与"序列被截断、还下不了结论"**
  （`ScreenOutput.Scan` 的 out 参数就是为此加的）—— 混成一个 `false` 会把全屏程序
  在块边界上**永久**误判成线性

### 9.2 输入：**逐键**，特殊键 = **ANSI 序列**

程序调 `getchar()`（`#5`）拿到的是**一个键**，不是一行 —— 交互式程序（`vim`/`top`/`mc`）
就是靠它工作的。**特殊键按 xterm 的老约定翻成 ANSI 序列**（跨语言契约）：

| 键 | 字符流 |
|---|---|
| Esc | `\x1b` |
| 方向键 | `\x1b[A` / `B` / `C` / `D` |
| Home / End | `\x1b[H` / `\x1b[F` |
| PgUp / PgDn | `\x1b[5~` / `\x1b[6~` |
| Delete | `\x1b[3~` |
| F1–F4 | `\x1bOP` `\x1bOQ` `\x1bOR` `\x1bOS` |
| F5–F12 | `\x1b[15~` `\x1b[17~` `\x1b[18~` `\x1b[19~` `\x1b[20~` `\x1b[21~` `\x1b[23~` `\x1b[24~` |

**为什么照 xterm 而不自己编号**：ncurses 那套程序本来就认这些序列，
自己发明一套等于让它们解不出来。附带好处是**软键盘、外接键盘、程序侧只有一种表示**。

⚠ **软键盘产生不了 Esc / 方向键 / F 键** —— 那些只有**外接键盘**才有
（软键盘只产生文字）。所以 `vim` 这类在手机软键盘上**退不出来**；
**第三种窗口（电脑屏）要配一排屏幕按键**，正是为了补这个缺口。

⚠ 目前**只有 Android 接了外接键盘**（`View.KeyPress`）；iOS/MacCatalyst/Windows 还没接。
（**窗口**那一路是另一个入口 —— `Activity.DispatchKeyEvent`，见"电脑屏窗口的键盘"一节。）
