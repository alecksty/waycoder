# 老程序兼容性调查报告

> 目标：**现成的老程序尽量不改就能跑**。本文是**实测报告**，不是评估——所有结论都有样本支撑。
> 最近更新：2026-09-21（v0.96.342）

## 一、结论：分四档，不是"能/不能"

| 档 | 类型 | 可行性 | 证据 |
|---|---|---|---|
| **A** | **纯字符界面**（curses / conio / ANSI 转义） | **高** | `tty-clock`（689 行）**源码零修改**编译+运行通过 |
| **B** | 用了 `termios` / `ioctl` 的终端控制 | **中** | `cmatrix`（894 行）卡在 `TIOCGWINSZ` / `O_RDWR` |
| **C** | x86 专属（DOS 内存模型、`bios.h`、`int86`、显存 `0xB8000`） | **低，且不该做** | `dos.h` 头文件里已明确排除 |
| **D** | 图形（BGI `graphics.h` / Allegro） | **低**，得重写成 `ui_*` | BASIC 的 PcGfx 路径往固定 DOS 地址写，照搬会"能编译画不出来" |

**一句话**：**A 档是大头，且已经跑通了**。DOS / Unix 时代的文本程序绝大多数落在 A 档。

### C 档的边界（用户 2026-09-22 定案）

> **直接操作汇编、直接操作内存的老程序就不支持，或者修改掉才能支持。**

这条把 C 档从"可行性低"明确成了**范围外**（不是"还没做"）。落在里面的具体形态：

| 形态 | 例子 |
|---|---|
| 直接操作汇编 | `asm` / `__asm__` 块、`__emit__`、寄存器伪变量 `_AX`/`_BX`/`_CX`/`_DX` … |
| 直接操作内存 | 显存直写（`0xB8000` 文本 / `0xA0000` 图形）、`bios.h`、`int86`、`peek`/`poke` |
| 裸硬件 | `interrupt` / `_interrupt` 中断处理程序、端口 `inp`/`outp`、`DEF SEG`（BASIC） |

⚠ 由此得出一条**实现纪律**：这些**不能**被当成"透明的空白"混过去。
新加的 `AttributeStrip`（见 `CCompiler/AttributeStrip.cs`）把 `__attribute__`/`__declspec`/
`__inline__`/`__restrict`/`far`/`near`/`huge` 按透明处理 —— 判据是「**丢掉不改变可观察行为**」；
而上面这张表里的东西**恰恰就是那个可观察行为**，丢掉会**静默编错**
（比直接编不过更糟：程序看起来能跑）。该改的是**程序自己**（把显存直写改成 `ui_*`、
把 `asm` 段改写成 C），不是把它们从语法里抹掉。

同源定案：`gfx_*`/显存/BGI 一整套不做（见本文件第七节）、QBasic 的 `SCREEN`/`LINE` 那套
往固定 DOS 地址写（`Examples/basic/` 里能跑的那几个都走 `ui_*`）。

排优先级用的判据（用户定的规矩：**哪些多就优先哪些**）—— GitHub 代码搜索含该头的 C 文件数：

| 头文件 | 文件数 | 状态 |
|---|---:|---|
| `conio.h` | 110,336 | ✅ 已做 |
| `dos.h` | 49,792 | ✅ 已做 |
| `curses.h` | 43,264 | ✅ 已做 |
| `ncurses.h` | 40,448 | ✅ 已做（转发 `curses.h`） |
| `graphics.h` | 8,336 | ⬜ 最后（D 档，需重写） |
| `windows.h` | 2,080,768 | ❌ **不做**（Win32 GUI，映射不到手机） |

## 二、真正的工作量在**环境补齐**，不在功能开发

三个样本合计要 20 个头，`Lib/c/` 已有 14 个。缺的 6 个里有 5 个是**小东西**：

| 缺的头 | 内容 | 成本 |
|---|---|---|
| `termios.h` / `termio.h` | `struct termios` + `TCGETS` 等常量 | 小（常量 + 空实现） |
| `sys/ioctl.h` | `TIOCGWINSZ`（问窗口尺寸） | 小（返回 80×25） |
| `fcntl.h` | `O_RDWR` / `O_CREAT` 等 | 小（常量） |
| `getopt.h` | 转发（`getopt` 函数**已实现**） | 极小 |
| `ncurses/curses.h` | 子目录形式，转发 | 极小 |
| ~~`windows.h`~~ | 条件编译用的 | **不做** |

**关键观察（说明为什么这条路可持续）**：`tty-clock` 那一轮补完
（`localtime` / `strftime` / `getopt` / `strdup` / `stat` / `select` / `sigaction` …）之后，
`cmatrix` **没有暴露任何新的函数缺口** —— 它报的全是**常量**和新头。
**边际成本在快速递减**，这正是兼容层该有的曲线：补的是**通用环境**，不是逐程序打补丁。

## 三、样本暴露的三类障碍（性质完全不同，对策也不同）

### ① 缺库（`cmatrix`）—— 最好办

补头 / 补常量，机械且一次投入长期受益。已形成流水线。

### ② 前端缺陷（`sl`）—— **最该修**

`sl`（295 行，经典蒸汽火车）卡在**词法阶段**：

```
词法错误 … 未知字符：\
```

但已二分证明：`sl.h` **单独 include 是好的**、宏里的 `\\` 也正常。
⇒ **这是 C 前端的问题，不是缺库**。

**影响面最大**：ASCII 画图程序里这种字符串遍地都是，修一处可能带好一批。

### ③ 实现细节（`tty-clock` 画面空）—— A 档的闭环

编译+运行都过、也进了主循环（`while(ttyclock.running)` 在跑）、`draw_clock()` 也确实调了
`wrefresh`，但**不输出任何东西**。怀疑 `newwin()` 的退化实现（返回 `stdscr`）
让它画到了别的行列上。

## 四、"一行不改"的正确形态

★ **缺的东西全在平台侧补，不动程序源码** —— 这是本报告最重要的一条方法论。

拿 `tty-clock` 补出来的环境缺口（**程序一个字符都没改**）：

- **头**：`ncurses.h`、`locale.h`、`sys/stat.h`、`sys/select.h`
- **常量**：`LC_TIME`、`A_BLINK`、`KEY_UP/DOWN/RESIZE/…`、`STDIN_FILENO`、`SIGSEGV/SIGPIPE/…`
- **只有声明没有定义**：`stdin`/`stdout`/`stderr`（`stdio.h` 里是 `extern`）⇒ 链接期缺符号
- **函数**：`localtime`/`gmtime`/`time`/`strftime`（自写日期算法、无时区）、`fprintf`、
  `strerror`、`getopt`、`strdup`、`atexit`、`nanosleep`、`sigaction`、
  `select`/`pselect`/`FD_*`、`stat`/`S_ISCHR`
- **curses 的宽字符变体**：`wattron`/`wattroff`/`wbkgdset`/`waddch`/`wgetch`/`box`/`wborder`/
  `newterm`/`set_term`/`use_default_colors`/`clearok`/`mvwin`/`wresize`/…

⚠ **`curses.h` 要带出 `stdio.h`** —— 真 ncurses 就是这么做的，而 `tty-clock` **自己并不**
include `<stdio.h>`，却用 `stderr`。这条不照抄，第一轮编译就报"未声明的变量 'stderr'"。

⚠ **`sigaction` / `select` 一律返回"成功"**：本平台没有信号、没有 fd 多路复用。
返回 -1 会让不少老程序当成致命错误**直接退出**；返回成功它们就正常往下走。

## 五、风险与判断

**A 档的可行性已经用 `tty-clock` 证明**（689 行真实程序，一行不改）。
剩下的不是"能不能"，而是"补多快"：

- **补头/常量**：机械，已形成流水线
- **修前端缺陷**（`sl` 那条）：**一次投入、全面受益**，优先级最高
- **`termios`/`ioctl` 垫层**：让程序"以为自己在跟终端说话"，实际映射到固定的 80×25
  —— 中等工作量，但一次覆盖 B 档

**唯一的风险**：C 前端里可能还有若干像 `sl` 这样的**静默/半静默缺陷**
（这类问题历史上都是"编译全绿、跑起来不对"）。
**唯一的发现方式就是继续抓真实程序** —— 判据不能只靠自写探针。

## 七、专题：C 语言**绘图类**程序能不能移植？

先分开：**"画字符"和"画图形"是两回事**，可行性差得很远。

| 类型 | 例子 | 可行性 | 说明 |
|---|---|---|---|
| **字符画**（ANSI / curses 画方块字符） | `cmatrix`、`sl`、`nyancat` | **高** | 本质还是文本，已归 A 档 |
| **BGI**（`graphics.h`） | DOS 时代 `initgraph`/`line`/`circle`/`setcolor` | **不做**（v0.96.351 定案） | 见下 |
| **Allegro / SDL** | 后期 DOS 游戏 | **低** | 自带音频/输入/定时器一整套运行时，等于重做一个平台层 |
| **直接写显存**（`0xB8000` / `0xA0000`） | 老 DOS 游戏 | **低，且不该做** | 那是硬件地址，手机没有对应物 |

### BGI 为什么说"可行"

因为它要的能力，**`ui_*` 原语已经全覆盖**，而且**已经在手机上跑通了**
（`draw_prims.c` / `draw_colors.c` / `draw_brush.c`，以及 `tetris` / `gomoku` 都是这批原语画的）：

| BGI | 我们已有 |
|---|---|
| `initgraph(gd, gm, path)` | `ui_win_open(title, w, h)` |
| `line` / `lineto` / `moveto` | `ui_line` |
| `rectangle` / `bar` / `bar3d` | `ui_rect` |
| `circle` / `arc` / `ellipse` | `ui_ellipse` / `path`（**BGI 没有的曲线我们反而有**） |
| `setcolor` / `setfillstyle` / `floodfill` | `ui_rect` 填充 + `gradient` |
| `outtextxy` / `settextstyle` | `ui_text` |
| `getmaxx` / `getmaxy` | `SCR_W` / `SCR_H` |

**工作量的本质不是"能不能画"，而是三件事**：

1. **坐标缩放** —— BGI 程序按 640×480 硬编码，手机画布尺寸不同。
   等比缩放，或按 `getmaxx()` 动态布局（后者更好，很多程序本来就是那么写的）
2. **窗口模型** —— BGI 是"独占全屏 + 自己管刷新"，我们是"开一扇窗口、`ui_present()` 才上屏"
3. **主循环** —— BGI 程序几乎都是"画完等按键"，要接上消息循环

三件都是**垫层**能解决的（照 `curses.c` 的做法：程序不改，我们把语义映射过去）。

### 判断

- **BGI 值得做**，排在 `termios`/`ioctl` 那批之后 —— 它是 `graphics.h` 8,336 的量，
  比 curses 小一个数量级，但**是"绘图类老程序"唯一的现实入口**。
- **Allegro / SDL 不建议做** —— 投入产出比太差，那已经不是"补环境"而是"移植一个平台"。
- ⚠ **要防一个坑**：BASIC 那边有前车之鉴 —— `SCREEN`/`LINE`/`CIRCLE` 那套 PcGfx
  **是往固定 DOS 内存地址写的**，照搬会得到"能编译、画不出来"。
  BGI 垫层**必须**走 `ui_*`，**不能模拟显存**。

### 定案（v0.96.351）：**`gfx_*` / 显存 / BGI 这一整套都不做**

用户原话：「**所有直接写内存来画图的接口都不需要了，过时了**」「gfx 那套没用，
现在是对接手机接口」。这条比上面那行更彻底 —— 上面说的还是"BGI 垫层走 `ui_*`"，
现在是**连垫层也不做**：

- **画图一律走手机接口**（`ui_*`，号段 500–599），那是这个平台唯一的绘图面；
- `Lib/shared/src/graphics.c`（VGA 引擎）、`graph.c`（BGI 门面）、`Lib/c/graphics.h`
  与 `gfx.h`（**本来就在 `third_party/vml/PRUNED.txt` 里**）——
  **保持现状，不补头文件、不挂链接、不修**。`Lib/c/graph.vml` 那份实现留在盘上不动它，
  但**没有任何 C 例子会去用**；
- ⚠ **别再照 `ROADMAP` 去把 `graphics.h` 从剪枝清单里捞出来** —— 这一条就是防止那种事。

**为什么**：那批程序的语义是"写一块固定地址的显存、宿主把它贴到屏幕上"，
而本平台的目标形态是"程序调宿主接口画"（与 `ui_*` 同一套）。两者是**两套并行的绘图面**，
只做后面那一套就够，做前面那套等于把一台 DOS 机的显示子系统搬过来。
**老程序的图形需求，走第三种窗口（电脑屏）+ `ui_*` 满足**，不走 BGI。

## 八、待查：**编译的非确定性**（比缺库严重得多）

⚠ 压样本时撞见的，**两次可对照的观察**：

- `m5b.c`（一个二维数组 + 含 `\\` 的宏）：同一份文件、同一条命令，
  先失败（`词法错误 … 未知字符：\`），随后**连续 5 次通过**
- `sl.c`：先失败，**连续 3 次通过**，再跑**又失败**（同样报第 125 行 131 列）

**⇒ 同一输入、不同结果 ⇒ 编译器侧存在非确定性。**

**为什么这条比"缺某个库"严重得多**：

- 缺库是**确定的**，补一次就永久解决
- 非确定性会让**真机上出现随机失败**，而且症状是"有时编译不过 / 有时跑不对"，
  极难归因 —— 本仓历史上最难查的一类

**已排除的方向**（都做过最小复现，全部通过）：
宏里的 `\\`、一行多个含 `\\` 的宏、二维初始化 + `\\`、`sl.h` 单独 include。

**下一步**：需要定位是**哪个环节**不确定 —— 预处理器展开顺序、多线程编译、
还是带缓存的中间结果。**在钉死之前，不要把它当成"偶尔抽风"放过。**

## 十一、2026-09-22：**命令行窗实时化** —— 一条一直没人当回事的拦路虎

### 症状

`cmatrix` / `tty-clock` 编译也过了、根因也修了，可**手机上跑起来运行期间屏幕是空的**。
查下来不是它们的毛病：

    CaptureIo 只往 StringBuilder 里攒        （MauiVml.cs）
      → RunProgram 跑完才判一次              （ScreenOutput.LooksFullScreen(整段)）
      → ShellPage.RunWithPromptAsync 整段 Append   ← var bodyText = (await body()).TrimEnd()

⇒ **程序跑完才一次性刷出画面**。而 PC/Linux/老 Mac 程序**绝大多数是终端程序**，
全是"不退出就一直画"（`top`/`vim`/`mc`）—— 这一类**一个都跑不起来**，
连 `q` 都按不出去（输入那边同样要"敲满一行按回车"）。

### 为什么它比"缺库"更难发现

它**不报错、不缺符号、编译全绿**。样本少的时候还看不出来 —— `sl` 那种"跑几秒就退出"的
程序，整段缓冲和实时出画**看起来一模一样**。只有"不退出就一直画"的才暴露。

**这是本档第一类"平台自身设计"造成的障碍**，与前面三类（缺库 / 前端缺陷 / 实现细节）
性质不同：那三类都是"程序缺什么我们补什么"，这一类是**宿主自己没做到位**。

### 修法（v0.96.351/352）

- 输出：`ShellStream` 状态机（探测 → 线性 / 网格）+ 输出泵（增量 + 节流）
  —— 网格是**替换那一块**，不是往后追加
- 输入：`KeyQueue` + 逐键直通（软键盘 `TextChanged` / 外接键盘 `View.KeyPress`）
  —— 特殊键按 **xterm 老约定**翻 ANSI（方向键 `\x1b[A`），不自己发明编号
- ⚠ **软键盘产生不了 Esc / 方向键 / F 键** ⇒ `vim` 这类在手机软键盘上退不出来，
  要么接蓝牙键盘，要么等第三种窗口配屏幕按键

### 顺带：三种窗口的划分（下一步）

主屏 = **命令行**（已有，实时化已完成）；**副屏才需要弹窗**，而弹窗分两种：

| 弹窗 | 面向 | 输入 | 坐标系 |
|---|---|---|---|
| 图形窗口（已有） | 触摸/手柄小游戏 | 触摸 + 手柄 | 自适应缩放，可跟随旋转 |
| **电脑屏窗口（已做）** | 固定分辨率的老图形程序 | 触摸→**鼠标**、软键盘 + 物理键盘 | **固定**为程序声明的分辨率，双指缩放/平移只是**显示变换**（缩放/平移**尚未接线**） |

电脑屏窗口已落地并上模拟器验过（`#582`、`Examples/c/pcscreen.c` 体检程序、
`scripts/maui-vml-verify/pcscreen_run.py`）。键盘两条路（屏幕键盘 81 键 + 外接物理键盘）
也已接通，见 [`VML宿主接口.md`](VML宿主接口.md) 的"电脑屏窗口的键盘"。

⚠ 顺带记一条既有遗漏：`DrawTextEx = 581` 没进 `VmlUi.AllNumbers`，
正是那段注释警告的"抢号护栏形同虚设"——加新号时要一起补。

## 九、实测样本战绩（滚动更新）

### 已解决①：**程序依赖构建系统定义的宏**（2026-09-22 修）

`cmatrix` 报的 `VERSION` **不是库缺失** —— 它是 Makefile 里 `-DVERSION="..."` 传进来的。
老程序的编译方式通常是 `gcc -DVERSION=\"1.2\" -DHAVE_CONFIG_H ...`，
而我们是"把源文件丢给 `vml run`"，**没有构建系统** ⇒ 这类宏全缺。

**这与"缺 `#include`"是不同性质的问题**（库补不了，得靠**喂编译宏**），
`autoconf` 时代的程序几乎都这样。**修法：`VMLTOOL_DEFINE` 环境变量**（见下）。

### 已解决②：**头"没被读到"其实是"配置没给"**（2026-09-22 修）

现象：六个头（`getopt.h`/`fcntl.h`/`sys/ioctl.h`/`termios.h`/`termio.h`/`ncurses/curses.h`）
**全都已经躺在 `Lib/c/` 下**，`TIOCGWINSZ`/`opterr`/`optarg` 却仍报"未声明"。

**真根因**是 `cmatrix.c:43` 的 **`#include "config.h"`**（**引号形式**，按尖括号
扫缺口时会整个漏掉），而它后面的 include **全部包在 `#ifdef HAVE_*_H` 里**：

```c
#ifndef EXCLUDE_CONFIG_H
#include "config.h"        /* autoconf 生成的，我们没有 ⇒ HAVE_* 全未定义 */
#endif
#ifdef HAVE_GETOPT_H
#include <getopt.h>        /* ⇒ 这一句和它后面五个头，一句都没进来 */
#endif
```

**`config.h` 的语义是"这台机器有什么"，与具体程序无关** —— 所以正解是在平台侧
提供一份（`Lib/c/config.h`），这与**交叉编译时提供 sysroot 描述**是同一件事。
`ResolveIncludePath` 不区分引号/尖括号，而 `Lib/c/` 在标准搜索路径里 ⇒ 放那儿就能被找到。
（程序**自己**目录下的 `config.h` 仍然优先，那是对的。）

⚠ **只写我们真有的**：定义错一个 `HAVE_XXX` 的后果**不是编译报错、而是静默走错分支**。
本次**刻意不定义** `HAVE_RESIZETERM`（`curses.c` 里还没有它，不定义会自动退到 `wresize`）、
`HAVE_SETFONT`/`HAVE_CONSOLECHARS`（Linux 虚拟控制台专有）、`HAVE_SETJMP_H`（没有那个头）。

### 已解决③：**`getchar()` 收不到 EOF** —— 老 C **最标准那句**读循环收不了尾（2026-09-22 修）

```c
while ((c = getchar()) != EOF) { ... }     /* 老程序里到处都是 */
```

这一句在本平台**永远不结束**：`getchar` 一直返回值、从不给 `EOF`，
于是程序一直转到宿主超时被掐掉（输出 `VM execution cancelled`，退出码非 0）。

**真根因不在宿主"不给 EOF"，而在它从没被问到。** `io.c` 的 `getchar` 写的是

```c
return asm("SYSCALL #5, ${1}");   /* 注释还写着"R0 必须显式给 1" */
```

而 asm 模板里的 `${...}` 是**变量替换**（`${ch}` → 该变量所在的寄存器，
见 `CodeGenerator.Statements.cs`）—— **`${1}` 不是变量名，于是什么都不生成**。
实测生成出来的函数体里 `syscall` 前面**一行都没有**（`git show HEAD:.../io.vml` 的
`getchar` 可查）。后果是 `getchar` 一直走**非阻塞**分支
（`bool blocking = registers[0] == 1;` 为假）：输入一空就 `R0 = 0` 返回 ——
**"读到的字符是 0"看起来就像"没有 EOF 这个信号"**，而宿主里那条
`InputExhausted` 分支**根本走不到**。

⚠ 这条注释是**代码从未实现过的意图**，而且**不报错**——`conio.c` 里
`asm("SYSCALL #5, ${0}")` 与那句"R0=0 ⇒ 非阻塞"是同一个错法
（它靠 R0 的**残留值**碰巧非阻塞）。**凡是靠残留寄存器碰巧正确的东西，
症状都是时序相关、最难查的那一类。**

**修法（两处，缺一不可）**：
1. `io.c` 的 `getchar` 改成**字面指令** `asm("MOVE R0 #1")`（照 `builtins.c` 的写法）
   + 走**新号 `SYSCALL #14`**；
2. `#14` = 与 `#5` **同语义**，唯一区别是"输入源耗尽时给什么"：
   `#5` 给空行（`0x0A`，那是给 `conio.getch()` 的单键读用的），`#14` 给 **`EOF`(-1)**。

⚠ **不能直接改 `#5` 去给 EOF**：`Lib/shared/src/readline.c` 的 `read_line`
靠 `c == '\n'` 收尾，`#5` 一给 -1 它就再也不会返回。老号语义一字不动，
EOF 语义由新号承载（房规：**新能力一律走新号**）。
⚠ 新号还必须登记进 `VMLRuntime/SyscallNumber.cs` 的 `SyscallConstants.UserAllowed`
—— 用户态只放行本表，漏了会打 `Permission denied: syscall 14 requires kernel mode`
并把 R0 置成错误码（表现同样是"读到的字符全是垃圾"）。

**验证**（`.scratch/stdin_min.c`，判据就是那句原样的读循环）：

| `--stdin` | 期望 | 实测 |
|---|---|---|
| `'ab'` | `[97][98][10]`、`N=3` 就停（10 = `ReadChar` 补的行末换行） | ✅ |
| `'ab\n'` | `[97][98][10][10]`、`N=4` | ✅ |
| 不给 | ⚠ **阻塞到 `TimeoutSeconds` 被掐**（`VM execution cancelled`） | 见下 |

⚠ **一条已知的语义边界**：`InputExhausted` 的契约是"**脚本化**输入读完为真、
交互式恒为假"（`_lines == null` 即"没有输入源"）。所以**不给 `--stdin` 时
`getchar` 会阻塞到 `TimeoutSeconds`**，而不是立刻 EOF —— 这是**有意的**
（交互终端上"没键"本来就该等用户，返回 EOF 会让每个交互程序都立刻退出）。
**但要验 EOF 判据就必须喂 `--stdin`**；这也是本次修 `getchar` 顺带改变的一条行为：
修之前它是**非阻塞**的（因为 R0 从没被置 1 ⇒ 没键立刻返回 0）。

## 十、2026-09-22 那一轮：从"编不过"到"能画"（`cmatrix` 全程）

样本 `cmatrix`（894 行）走完了从**报 7 个错**到**编译 + 运行 + 逐帧绘制**的全过程，
中间压出**五个真缺陷**。这一节按"发现顺序"记，每条都是**别的老程序也会撞上**的。

### ① `\033` 八进制转义被解析成 **NUL**（C 前端，影响面最大）

```c
puts("A\033[31mB");   /* 实得 `A` —— puts 在 NUL 处截断 */
```

`Lexer.cs` 里**三处**转义解析（字符串 / `ParseEscapeSequence` / `ReadChar`）
**各写了一份**，而**每一份**都有一个 `case '0': … '\0'` 的**抢先分支**把 `\033` 截成
`NUL + 字面 "33"`。**C 标准里 `\0` 本来就是八进制转义（值 0）**，那个分支纯属多余 ——
删掉它、让八进制路径统一接手，`\0` 与 `\033` 就都对了。三份实现也收敛成了一个
`ParseOctalEscape`。

⚠ **这类问题的判据不能靠"看起来对"**：`Examples/c/ansi_colors.c` 里早就记着
"必须用 `\x1b`、不能用 `\033`" —— 那是**绕开**而不是修。`\033` 恰恰是老程序
写 ANSI 转义的**最常见**写法，所以**绕开等于把一整类程序挡在门外**。

### ② `VMLTOOL_DEFINE`：喂构建系统宏的入口

与 `VMLTOOL_INCLUDE` 同一族，**换行**分隔（不用分号 —— 宏值本身常含分号）：

```bash
VMLTOOL_DEFINE=$'VERSION="cmatrix 2.0"\nPACKAGE="cmatrix"'
```

落在 `CompilerHelper.ApplyEnvDefines`（**两条 Preprocessor 路径共用一份规则**）。
只有名字没有 `=` 的按 C 命令行惯例取 `1`。

### ③ **`wgetch` 必须先刷新窗口** —— "画面空"的真根因

`cmatrix` / `tty-clock` 的主循环里**一个 `refresh()` 都没有**（实测 cmatrix 全文只有
3 处，全在 `finish`/`c_die`/`resize_screen` 里）。它们靠的是 ncurses 的**文档化行为**：

> If the window is not a pad, and it has been moved or modified since the last call to
> `wrefresh`, **`wrefresh` will be called before another character is read**.

漏掉这一步的症状极具迷惑性：**进程活着、计时器在走、`addch` 也在改缓冲，屏幕上一个字不出**
（一度怀疑到 `newwin` 的退化实现上，那是错的）。

### ④ **`kbhit()` 必须真的查询宿主** —— 动画程序的节拍器

旧实现只查自己的行缓冲，空缓冲恒返 0，还留着一句注释说"按行的 stdin 无法预知有没有按键"——
**那句是错的**：宿主本来就有 `ISystemCallHandler.KeyAvailable()`，而 `SYSCALL #5` 的
`R0=0` 模式就是"非阻塞地取一个字符"。

后果不是"偶尔不准"而是**整类动画程序跑不起来**：主循环写成
`timeout(0); … if ((ch = wgetch(stdscr)) != ERR) {…}`，靠"没键"推进每一帧；
`kbhit` 恒 0 ⇒ `getch` 每次都阻塞读一整行 ⇒ **一帧都画不出来**。

配套修了两处（**缺一不可**）：
- `io.c` 的 `getchar()` **必须显式 `R0=1`** —— 不给的话 R0 是上一句残留值，
  而 `kbhit()` 恰恰会先把它置 0 ⇒ `getchar` 退化成"没键就返回 0"（**时序相关的难查故障**）
- `ISystemCallHandler.InputExhausted`（新默认成员）—— 把"**此刻**有没有键"与
  "**还有没有可能**来键"分开。脚本化输入读完 ⇒ 阻塞读给"空行"收尾，**别死等**
  （`KeyAvailable` 恒 true 那个旧妥协正是为了掩盖这个洞，代价是 `kbhit` 全废）

### ⑤ 新增的库函数（`cmatrix` 逐个压出来的）

`rand`/`srand` · `strcasecmp`/`strncasecmp` · `vfprintf` · `ttyname`/`isatty` ·
`leaveok`/`scrollok`/`idlok`/`raw`/`noraw`/`nonl`/`savetty`/`resetty` · `timeout`/`wtimeout` ·
`napms` · `standout`/`standend`/`beep`/`flash`/`has_ic`/`has_il`/`wnoutrefresh`/`doupdate` ·
`A_ALTCHARSET`/`A_CHARTEXT`/`A_ATTRIBUTES` · `TRUE`/`FALSE` · `SIGWINCH`/`SIGTSTP` 等
**整张信号表** · `signal`/`raise`。

⚠ 其中 `rand` 是**"声明了却一直没实现"**（`stdlib.h:48` 早就声明了它）——
症状是**一路编到链接期**才说"未定义的函数 'rand'（引用 15 次）"。
**声明了就得有实现**，缺一个都会在真程序上现形。

### 仍未结（两条，都与**输出编码**有关）

**A. ~~`addwstr` 有问题~~ —— 假的，是**我自己的两个错误**叠出来的**

**这一条的结论全部作废。** `addwstr` 从始至终是**对的**（现在 `m65.c` → `41`、
`m1.c`/`likecm.c` → `01`、`two.c` → `C3 A4`，全对）。我追了十几轮的"多字节垃圾"是两件事叠的：

1. **一个忘了删的探针**：早期为看 `cp` 的值加过
   `addch(cp & 0xFF); addch((cp >> 8) & 0xFF); …`（把 `cp` 的 4 个字节逐个 `addch`），
   **它就在被测函数体内** ⇒ 我一直在**测自己的探针**。`sc_ch[0..3] = 1,0,0,0`（探针写的）
   + `sc_ch[4] = 1`（真正的 `addch`）＝ 我看到的 `01 00 00 00 01`，**完全吻合**。
2. **判据偏移错了一个字节**：`find(b'[40m')+5` —— `[40m` 是 **4** 字节，该 `+4`。
   于是我把紧跟其后的那个字符（`41`='A'）一并跳过了，看到的全是空格。

⚠ **教训（比这次的具体 bug 值钱）**：
- **临时探针要么立刻删、要么带上显眼的标记**，别留在被测函数体里 ——
  **观测者效应**在"插桩改的是被测对象的输出"时尤其致命（本仓记过
  "判据装置自己骗人比代码出错更难查"，这次是我自己成了那个装置）。
- **判据的偏移量要按字节数算，别凭印象** —— `[40m` 是 4 字节不是 5。
- 两条合起来的效果是：**一个不存在的 bug 被"稳定复现"了十几轮**。
  这正是为什么每条结论都要**换一个独立路径再验一次**。

**B. UTF-8 多字节序列被拆散 —— 已修**（2026-09-22）

**症状**：`addch(0xE4); addch(0xB8); addch(0xAD);` 出的画面是 U+FFFD。

**两个根因，都在 `curses.c` 里，都是"字节落位"的错误**（与"编码支持"无关）：

1. **`addch` 里那条"UTF-8 续字节（0x80–0xBF）不推进光标"的规则放错了层。**
   它本意是让多字节字符只占一列，但它改的是 **`addch` 这个公开语义**
   （ncurses 的契约是"一次 `addch` = 一个字符 = 一列"）。于是
   `addch(0xB8)` 与随后的 `addch(0xAD)` 落在**同一个 `sc_cx`** 上，
   `B8` 被 `AD` **覆盖** —— host 只收到 `E4` `AD`，
   而孤立的续字节只能解成 U+FFFD。
   判据：host 探针日志逐字节可见（`ch=-28 (0xE4)` 之后直接是 `ch=-83 (0xAD)`）。

2. **重构时的 `sc_putwchar` 让三个字节写同一个格子** ——
   又一次"一个码点占一列"的直觉。但**`sc_ch` 是字节数组**，
   `refresh()` 就是"把这一行的 N 个字节原样发出去"，终端再按 UTF-8 合成字形
   ⇒ **一个字节 = 一个缓冲位置**才自洽。

**修法**（`curses.c`）：
- 抽出 `sc_cell_byte`（写一格，不推进）与 `sc_advance`（推进一列）两个原语
- **`addch` 恢复"一次调用 = 一列"**，不再有续字节特例
- `sc_putwchar`（`addwstr` 用）**逐字节走 `addch`**

**验证**：`tri.c` / `w0.c` / `wz.c` / `two.c` / `m65.c` / `likecm.c` **全部正确**。

**唯一仍"错"的是 `one.c`（单发一个孤立续字节 `0xB8`）→ U+FFFD —— 那是正确的降级**：
孤立续字节本身就不是合法 UTF-8 序列的开头，正常程序不会这么发。
（host 的 `ExpectedUtf8Bytes` 对它返回 1 走单字节解码，行为合理，**不改**。）

### 十一、cmatrix 仍未画出矩阵（进行中）

修完 UTF-8 之后 `cmatrix` 依然只输出**一整屏空格**（2000 字符）+ 3 处 `01 00 00 00`，
**没有任何矩阵字符**。目前掌握的线索：

- 输出结构是 `initscr` 的清屏 → 一次 `refresh` 的整屏 → `endwin`，**27 个光标定位序列**说明
  主循环转了几帧，但每帧内容几乎全空。
- `01 00 00 00`（整数 1 的小端）出现在**第一行第 30 列附近** —— 与
  `likecm.c` 当初那个"假象"长得一样，但这次 `curses.c` 里的探针已确认清零，
  所以它是**真实产生**的。
- `var_init()` **只初始化偶数列**（`for (j = 0; j <= COLS-1; j += 2) matrix[i][j].val = -1;`），
  奇数列的 `val` 依赖 `malloc` 的**零初始化**。

**试过但不成立**：给 `AllocateMemory` 加 `Array.Clear`（想对齐真机 `mmap` 的"新页是零"）——
**反而把 cmatrix 从 2580 字节变成 21 字节**（程序直接退出，无报错）。已**回退**。
⚠ 这又是一次"**假设未验证就动手**"：改动之前没有先证明"cmatrix 的异常确实来自未清零的内存"。
**下次先做判据**（例如在 `var_init` 之后把 `matrix[0][1].val` 打出来），再决定改不改。
