# vml-vmb-check —— VMB 编解码穷举往返检

```bash
dotnet run --project scripts/vml-vmb-check
```

把**每一个 opcode** × **每一种操作数编码形式**（寄存器 / 各宽度立即数 / 绝对与寄存器相对内存 /
标签 / 间接寻址）装进一个 `VmlProgram`，`ToVmbBytes()` 成 `.vmb` 字节，再 `FromVmbBytes()`
读回来，**逐条比对操作数**；数据段则**逐字节比位模式**。

- 通过：打印 `✔ 全量往返一致`，退出码 0
- 失败：逐条列出「原 → 读回」，退出码 1

## 为什么要穷举而不是"拿个真程序跑一遍"

真程序只覆盖它用到的那些编码。2026-09-19 修 `.vmb` 装载时抓到的四处不对称里，
**有两处正是抽查漏网的**：

| 处 | 现象 | 抽查能不能发现 |
|---|---|---|
| 偏移 ≥ 128 的寄存器相对寻址被误判成间接寻址 | 整条字节流错位 | ❌ 要恰好用到 ≥128 的偏移 |
| 负偏移符号位解反（`[R12-24]` → `[R12+24]`） | 局部变量与参数全指错，**不抛异常** | ❌ 要恰好用到负偏移 |
| 数据段数组读不回来 | 抛 `Unknown data type tag: 0x40` | 只有用到数组才炸 |
| 数据段不认 `long` | 抛 `Unsupported data type: System.Int64` | 很常见（C 标准库到处是 64 位常量） |

## 两条判据上的坑（都已体现在代码里）

1. **只比"指令条数"是无效判据** —— 解码错位时条数常常照样对得上。
   第一版就是只比条数，于是 `[R12+200]` 单独一条也"✔ 通过"。
2. **伪指令不写进 VMB**（`label`/`break`/`dump`/`trace`/`asm`/`chipasm` 由 `WriteCodeSection` 过滤），
   穷举时要跳过 —— 否则"读回来少了 6 条"会被误判成 bug。

另：`long` 走的是 double 那一路编码（tag 0x10 + 8 字节小端）。装载侧对 tag 0x10 是
**逐字节搬运、不按数值语义解释**，所以位模式原样保留、等价；但 `FromVmbBytes()` 返回的字典里
装的是 double，`ToString()` 看着天差地别（`1234567890123` → `6.1E-312`）。
**判据因此比字节，不比数值。**
